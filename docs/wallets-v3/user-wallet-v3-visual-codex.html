Wallet v3: how the architecture, permissions, and implementation plan fit together

This page explains the proposed new wallet generation using diagrams and concrete examples. It combines the current governing architecture, the draft implementation roadmap, and the owner-approved permission decision record. It does not authorize contract changes or deployment.

1 · Status and sources

What is decided, and what is not

The documents have different authority. This page uses the approved permission decisions as the latest overlay, but it does not silently rewrite the governing Markdown.

Governing

Architecture direction

The incremental routed-action architecture is owner-selected. It defines the wallet, registry, extender, Lego, session, capability, and settlement model.

Draft roadmap

Implementation packages

The work sequence is defined as small evidence-gated packages. Only the catalog-strip measurement is complete. Contract implementation remains unauthorized.

Owner-dispositioned

Permission decisions

Sixteen categories, parallel routed fields, explicit scopes, cumulative composite checks, narrow recovery, and future authority boundaries are approved pending propagation.

Important document boundary

If the approved permission record and the older provisional permission section disagree, this page shows the approved decision and labels it as awaiting governing-document propagation. The site is a review aid, not a new source of contract authority.

2 · One-picture model

The wallet stays the authority boundary

New actions can be registered without adding another hardcoded wallet function, but only the wallet can authenticate the caller, interpret permissions, open a session, create token authority, and settle the result.

Routed action path

Calls move left to right. Funds remain at the wallet until the capability is consumed.

The design rule

Actions are open-ended. Authority is not. A new action fits only when existing permission categories, policy inputs, spend primitives, session mechanics, and settlement modes can describe it. Otherwise the action stops for a reviewed core change.

3 · What changes

Incremental change, not a replacement policy system

The new generation is derived from the existing wallet trunk. Existing deployed wallets keep their current behavior.

Preserved

What stays in place

  • Wallet custody and accounting
  • Existing manager activation, expiry, limits, and cooldowns
  • Allowed assets, Legos, payees, and approved opportunities
  • Sentinel and wallet-backpack responsibilities
  • Direct transfers, cheques, payees, Billing, freeze, and recovery rails
  • Existing owner/security administration paths

Added for routed actions

What is new

  • Immutable bytes32 actionId records
  • Parallel manager/global routed permission masks
  • Exact manager action-ID approval
  • Bounded extender prepare
  • Transient session phase and one-time capability consumption
  • Capability-aware Legos that pull exact wallet-resolved amounts
  • Fixed wallet-owned settlement recipes

Existing wallets

Unchanged

They continue using the legacy action catalog. No migration design is part of this plan.

New wallet generation

Routed kernel

New wallet and Config blueprints receive the session engine and bound registries.

Direct rails

Remain direct initially

Payments and security operations do not enter the action registry during Phase 1.

Complexity deliberately left out

No policy DSL

Extenders cannot register new permission, limit, risk, or settlement meanings.

No arbitrary executor

No manager-selected target and calldata, generic raw-call bridge, or open consumer address.

No mutable action code

New meaning, schema, extender, or consumer implementation receives a new reviewed identity.

No generic persistence

No persistence mask or umbrella standing-authority permission. Concrete future effects stay typed.

4 · Authorization gates

A manager must pass all three layers

Action IDs answer “which exact procedure?” Permission bits answer “which type of authority?” Existing scopes and limits answer “with which assets, integrations, recipients, values, and timing?”

Gate 1

Exact action ID

The manager must hold the exact immutable action ID. Action IDs never support ANY. A new extender, schema, or meaning receives a new ID.

Gate 2

Every required permission bit

The immutable ActionSpec supplies one exact static mask. Both manager and global routed masks must cover the full requirement.

Gate 3

Existing policy and limits

Assets, Legos, payees, opportunities, cooldowns, transaction counts, USD limits, price, approved-vault, swap-count, and slippage rules still apply.

exact actionId approved
AND
manager mask covers exact required mask
AND
global mask covers exact required mask
AND
all manager/global scopes and existing limits pass

Parallel storage

Routed fields sit beside legacy fields

The new Config stores routed masks, action IDs, and explicit scope codes separately. Legacy direct-wallet structs remain authoritative only for the direct path. No live authority has two independently editable sources.

Grant-time safety

No dormant future bits

Config rejects unsupported bits when a grant is created or updated, not only when an action is executed. Expanding the supported mask later cannot silently activate a pre-granted bit.

Explicit scope codes

Empty lists never carry an inferred meaning in Wallet v3.

NONE = 0 No asset, Lego, or payee in this scope is allowed. Stored list must be empty.
SET = 1 Only exact members of the bounded stored set are allowed. Set must be nonempty.
ANY = 2 Any item in this policy dimension is allowed. Stored list must be empty.

Manager and global asset, Lego, and payee scopes apply cumulatively. Unknown codes reject. Action IDs remain exact-only and do not use these scope codes.

5 · Permission vocabulary

Sixteen approved categories

“Initial vocabulary” means the durable category is assigned, not that it is live in Phase 1. The first routed supported mask may contain only YIELD. Every other category remains unavailable until its reviewed enforcement package exists.

Bits 16–255 are unassigned

There is no generic PERSISTENT_EXTERNAL_AUTHORITY permission. “Persistent authority” is a security classification. A concrete future token allowance, protocol operator, governance delegate, or session-key design needs its own narrow owner-approved category and lifecycle package.

6 · Permission composition

One action can require several categories

Composite authorization is the union of every required permission bit plus cumulative application of every relevant limit. An intermediate swap cannot hide value from asset, recipient, or value ceilings.

Rebalance and deleverage can each be one action

“One action” means one immutable action ID, one wallet session, one consumer, and one capability consumption. The Lego may perform several protocol calls inside that session. It does not call nested wallet action functions.

7 · Transaction flow

8 · Extender and Lego

Typed preparation, then reviewed execution

The extender explains one approved action shape. The Lego executes the multi-step protocol workflow. Neither receives custody or a generic call grant.

  • No arbitrary target and calldata executor

What “typed facade” means here

SDK methods such as buildYieldDeposit(...) or buildDebtDeleverage(...) make the generic executeAction(actionId, actionData, deadline) entry point readable and safe to use. The facade is an offchain builder, not a second onchain authority source. New action IDs remain the controlled escape hatch.

9 · Funds and allowance

Where the money is at each moment

Custody remains at the wallet. The extender never holds user funds. A Lego receives only the transaction-scoped token authority the wallet resolved and committed.

Before consumption Funds at wallet · allowance 0 · session committed but authority inactive
During Lego execution Exact approved allowance activates only for the exact consumer and resolved amount
Before settlement calls Allowance returns to 0 · resulting funds or position belong to the wallet

First Phase 1 fund flow: yield deposit

The first slice creates no external operator grant and requires only YIELD.

→
Yield Lego Consumes capability and pulls only the resolved USDC
→
Yield protocol Deposit executes through the reviewed integration
→
Wallet position Vault/position token or wallet-owned position returns to custody

10 · Settlement and price

The wallet computes the result

Extenders choose only a wallet-supported settlement mode. They cannot register a new accounting language or tell Sentinel an unverified transaction value.

Observed inputs

Wallet-owned evidence

Starting balances, capability ledger, final balances, position/debt state, and fixed recipe data.

Valuation

Appraiser under a closed price code

Settlement derives policyChargeUsd and any required swap inputs/outputs.

Policy result

Existing limits update once

Per-transaction, period, lifetime, vault, swap-count, and slippage checks use wallet-derived values.

Default

PRICE_REQUIRED

Missing, stale, invalid, or zero price rejects when a price is required. The routed path does not weaken a USD limit by substituting zero.

Narrow recovery exception

NATIVE_BOUNDED_RECOVERY

Only an exact immutable pure no-conversion YIELD_EXIT or LIQUIDITY_EXIT recipe may use native-unit ceilings and wallet-observed recovery postconditions. Changing the price code requires a new action ID.

11 · Action lifecycle

Action code is append-only; lifecycle only narrows

An action ID pins one meaning, schema, extender address, extender codehash, exact permission mask, settlement mode, and entry/exit relationship.

PENDING Registered, review delay running, not executable
→
ENABLED Normal action use is allowed when wallet policy also passes
→
EXIT_ONLY Only non-expanding unwind use survives
→
DISABLED Terminal; re-enable requires a new action ID

The arrows show the longest narrowing path. PENDING may move directly to DISABLED, and ENABLED may move directly to DISABLED. No state may return to an earlier state.

New code means a new ID

A material action meaning, argument schema, or extender change cannot be installed behind an existing manager grant. The manager must explicitly approve the new action ID.

Entries name reviewed exits

An action that opens or expands a persistent position names immutable exit action IDs. Disabling the last usable exit must also disable dependent entry actions unless an approved owner-only recovery path remains.

12 · Persistent effects

Phase 1 is deliberately narrow

The first yield deposit creates only the expected wallet-owned yield position. It does not add a new delegated authority or administrative object.

Phase 1 may create

Wallet-owned yield position

One reviewed deposit action, one capability-aware Yield Lego, fixed settlement, and the existing owner exit/recovery path.

Phase 1 does not create

New standing or deferred authority

  • Standing allowance or reusable operator right
  • Offchain signature or bridge message
  • Governance vote, proposal, or delegation
  • New payee, revocation scope, or payment commitment type
  • Stream, subscription, third-party pull, or wallet-funded fee

Later permissions have closed meanings

PAY_NETWORK_FEES

Additive to the complete parent mask; never standalone. Future package binds mechanism, recipient, and caps.

ENROLL_PAYEE

Creates only a probationary, expiring, exposure-bounded payee. It does not authorize payment.

REVOKE_CLAIMS

Reduction-only across owner-designated source manager/epoch pairs. It cannot create or enlarge a claim.

CROSS_CHAIN

Always distinct, then cumulative with TRANSFER, TRADE, or fees required by local effects.

OFFCHAIN_SIGNATURE

Typed and cumulative with the authority created. Arbitrary bytes, hashes, and generic signing are prohibited.

GOVERNANCE

Separate from wallet administration and cumulative with signature, delegation, or other effects.

4 · Other families
Future summaries

Expand only after the trunk is ratified

Simple swaps, liquidity, rewards, and other actions that fit the approved authority and settlement vocabularies. Payments remain separate.

Change reach by artifact

New-generation only

Wallet + Config + provider

Fixed into newly created Wallet v3 instances; existing deployed wallets do not receive the routed kernel.

Replaceable per wallet

Sentinel + HighCommand

New routed entry points use existing backpack replacement paths, with direct behavior regressed separately.

Shared governance

LegoBook protection

No-repoint rules affect shared registry behavior and therefore receive an isolated blast-radius review.

Integration specific

Extenders + Legos

Each action and consumer implementation is reviewed, codehash-pinned, measured, and lifecycle-gated.

Current practical next step

The next implementation package is still Phase 0A baseline evidence. Before 0B, the approved permission record must be independently re-reviewed and propagated into the governing architecture and roadmap. This website does not skip that document gate.

14 · Evidence gates

Every package has the same contract

A package exists to answer one falsifiable question. It cannot quietly grow into the next package or treat a passing test as deployment authorization.

Package record

  1. Exact entry evidence and prerequisite commit
  2. Question answered
  3. Changed and untouched surfaces
  4. Fund and authority flow
  5. Security invariants and tests
  6. Size, gas, calldata, and shared-contract measurements
  7. Rollback and evidence record
  8. Independent review and disposition

Phase 1 stays unshipped

Registry, Config, Sentinel, LegoBook protection, wallet kernel, extender, and Lego candidates are reviewed separately but remain one unshipped candidate until Phase 1D.

  • No dormant registry deployment
  • No early shared LegoBook production change
  • No partial Config field rollout
  • No live funds or governance calls during development

15 · Trust boundaries

What the wallet proves, and what reviewed code must provide

The design does not claim the wallet can infer arbitrary protocol semantics. It narrows trusted code and makes its authority explicit.

Boundary Wallet-enforced Reviewed-code or external trust
Action identity Exact ID, immutable spec, lifecycle, extender codehash, exact static mask Governance review correctly classifies the action before activation
Policy Manager/global masks, exact action set, explicit scopes, existing limits Sentinel and Config implementation correctly apply the approved semantics
Prepared action Bounds, exact decode, complete commitment, resolved Lego IDs, codehashes Pinned extender declares the complete touched-asset and integration set
Token authority Exact resolved spend, exact consumer, single consumption, cleanup before settlement Token and protocol behavior match reviewed integration assumptions
Settlement Closed mode, wallet observations, price code, post-action limits, counters once Appraiser price correctness and reviewed protocol state observations
Governance Monotonic lifecycle and fail-closed unknown values Registry, LegoBook, backpack, and template governance execute reviewed changes
Independent legacy hardening item

The owner classified direct ETH/WETH wrapping and unwrapping as exchanges requiring canBuyAndSell, and selected a fail-closed unknown direct-action default. That product decision does not itself authorize editing or deploying the current Sentinel contract; it needs a separate regression-tested hardening package.

16 · Remaining decisions

The approved taxonomy and representation no longer belong on the open list. The following choices still need exact evidence or owner disposition at their named gates.

  • First yield-deposit settlement/valuation recipe and declared-set completeness proof
