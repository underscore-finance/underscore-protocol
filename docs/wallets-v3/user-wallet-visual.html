1. Mental model

Start with one distinction: the call path is not always the fund path. Config and extenders participate in deciding and describing an action, but they do not receive persistent custody.

The shortest accurate description

The wallet holds the user’s assets. Config answers whether a request is allowed. An extender translates a typed request into one bounded capability. A Lego uses that capability against one protocol. The wallet verifies the result and removes temporary authority before the transaction succeeds.

2. Components and responsibility boundaries

Only the wallet is intended to persistently hold user funds. The other components are policy or integration code.

Available versus reserved funds

A payment commitment does not necessarily move tokens immediately. It marks part of the wallet’s balance as unavailable to other actions.

available(token) = max(balanceOf(wallet) − reserved(token), 0) Example: 1,000 − 200 = 800 available

Direct transfers, new spend approvals, and new commitments are all bounded by this available amount. They cannot use the reserved portion.

3. Wallet state and execution phases

The wallet has persistent state that survives transactions and transient state that exists only while one routed action is executing.

State category Examples Lifetime Why it exists
Custody / policy config, token balances Persistent Stable custody with replaceable policy.
Attachments / routing family, version, extender, Lego, codehashes, selectors, lifecycle Persistent, append-oriented Know which typed code may open each action and which old exits remain.
Payments reserved, commitments, used ids, digests, nonces Persistent Prevent overspending, replay, and commitment resurrection.
Execution frame phase, caller, Config snapshot, attachment, selector, action id, nonce Transient Bind every nested call to one top-level request and block nested sessions.
Capability effect, consumer, target, resource, max amount, beneficiary, semantic hash, consumed bit Transient Permit one exact effect, then disappear.

Phase paths

Direct transfer

IDLE → DIRECT → IDLE

One policy check and one exact token transfer.

Routed action

IDLE → DISPATCHING → ACTIVE → SETTLING → IDLE

Route, policy, capability, effect, cleanup, and postconditions.

Commitment update

IDLE → COMMITMENT → IDLE

External sync, expiry, partial settlement, or refund.

Administration

IDLE → ADMIN → IDLE

Config replacement or extender attachment.

Why phases matter

Every stateful top-level action must start in IDLE and moves to a non-IDLE phase before its first external call. A reentrant callback cannot start a second transfer, routed action, commitment update, or admin operation.

5. Payment commitment states

The two payment modes share wallet-held reservation accounting but have different settlement mechanisms.

External exact (x402 onchain leg)

LIVE → proof used → USED
LIVE → expired + proof unused → EXPIRED

USDC pulls before wallet sync. Until sync, the reservation remains and conservatively reduces other spending capacity.

Reserved transfer (MPP model)

LIVE → full settlement → SETTLED
LIVE → owner releases remainder → REFUNDED

Partial settlement keeps the commitment LIVE while decreasing both remainingAmount and reserved[token].

“MPP” is deliberately narrow here

The PoC models reservation, cumulative partial settlement, and refund. It does not implement MPP HTTP challenges, credentials, receipts, or a production payment-method specification.

6. The action capability envelope

A routed extender proposes one ActionEnvelope. Config authorizes it, the wallet stores it transiently, and the actual Lego or named core primitive must match it before creating the effect.

actionIdWhich typed action is being performed, such as yield deposit (1) or borrow (10).
effectClassSPEND, LIABILITY, ASSET_RELEASE, or AUTHORITY.
consumerThe pinned Lego, zero for a named core primitive, or zero for a no-effect measurement route.
targetThe vault, debt protocol, token, or fixed authority target.
resourceThe ERC-20 or asset whose amount is being bounded.
maxAmountMaximum token loss, liability, release, or commitment amount.
beneficiaryWho must receive the result: usually the wallet, a permitted consumer, or an allowlisted recipient.
actionDataHashHash of action-specific fields not fully described by the common envelope.
Consumer mode Who consumes Examples Successful return rule
LEGO The attachment’s pinned Lego through consumeCapability. Yield deposit, borrow, repay, collateral release. Must consume exactly once.
CORE A named wallet primitive validates and consumes internally. Debt operator grant/revoke, x402 commitment, reserved transfer. Must consume exactly once.
NONE Nobody. Test-only empty-session measurement. Must remain unconsumed and create no economic effect.

9. What the PoC result means

Supported by the PoC evidence

  • Stable non-proxy custody with directly replaceable wallet-bound Config.
  • Typed, codehash-pinned extenders and selector-bounded DRAIN_ONLY succession.
  • One transient capability with exact approvals, semantic binding, and cleanup.
  • Wallet-held reservations and terminal payment non-reuse.
  • Base USDC EIP-3009 external-pull onchain leg.
  • Representative partial reserved-transfer settlement and refund.
  • All Q1–Q8 evidence questions passed.

Not established by this PoC

  • Production readiness, frozen ABI/storage, or audited deployment.
  • General execution, callbacks, receivers, or general EIP-1271.
  • Full x402 HTTP/facilitator or full MPP wire-protocol compliance.
  • Production Lego governance or malicious-Lego containment.
  • Real Ripe/Morpho safety.
  • Owner rotation, pause, emergency recovery, or full migration.
  • Native ETH, NFTs, swaps, liquidity, or nonstandard ERC-20 behavior.
Current architectural conclusion

Keep the custody, Config, typed attachment, capability, and reservation ideas. Redesign routed-session cost, payment-creation cost, adapter governance, emergency policy, and production payment liveness before a production specification.

10. Glossary

Config
Replaceable policy contract that returns yes/no authorization answers.
Attachment
Versioned record connecting selectors to an extender and its pinned dependencies.
Extender
Typed contract that translates function arguments into one action envelope.
Lego
Protocol adapter trusted to consume the capability before the external effect.
Capability
Transient permission for one action, effect, consumer, target, resource, amount, and beneficiary.
Semantic hash
Domain-separated commitment to the complete action envelope and routed frame.
Reservation
Wallet accounting that makes committed token value unavailable to other spending.
Commitment
Persistent payment record with mode, lifecycle state, amount, and destination.
DRAIN_ONLY
Superseded attachment lifecycle permitting only predeclared exit selectors.
ERC-1271
Contract-signature interface used narrowly here for one stored external-payment digest.
EIP-3009
Token authorization standard used by Base USDC for the external pull.
Terminal state
USED, EXPIRED, SETTLED, or REFUNDED; cannot return to LIVE.
