# User Wallet Transfer Gas Profiling and Optimization Report

**Date:** 2026-07-11  
**Repository:** `underscore-v2`  
**Branch at document creation:** `wallets-v3` (the commit hash below is the authoritative code reference)  
**Commit analyzed:** `cce97d56b62f58c0c3eeddb8fc551d1723bf0fc3`  
**Primary scope:** User-wallet payments through `UserWallet.transferFunds`, including whitelist transfers, registered payees, cheques, Billing pulls, and agent-mediated payments  
**Status:** Analysis and recommendations only; no protocol contracts were modified

---

## 1. Executive Summary

The actual ETH or ERC20 transfer is not the primary gas cost in the user-wallet payment flow. Most gas is consumed by the authorization, pricing, configuration, recipient-limit, wallet-accounting, and deposit-points machinery that surrounds the transfer.

The measured steady-state owner-to-whitelisted-recipient ERC20 payment costs:

- `351,839` gas of contract execution.
- `373,839` gas as a direct-transaction-equivalent result after adding intrinsic transaction gas.
- Only approximately `10,194` gas for the repeat ERC20 `transfer` itself.

The strongest single finding is that the owner path loads three large manager data structures before Sentinel recognizes that the signer is the owner:

| Owner-path manager retrieval whose full structure is unnecessary | Measured gas |
|---|---:|
| Global manager settings getter; only `canOwnerManage` is needed | 58,201 |
| Signer-specific manager settings getter | 56,625 |
| Manager period data getter | 15,488 |
| **Total** | **130,314** |

This is approximately:

- `37.0%` of the steady owner transfer's contract execution.
- `34.9%` of its direct-transaction-equivalent gas.

The highest-priority optimization is therefore an owner-specific authorization fast path that runs before manager structs are retrieved. The current three-getter burden is directly measured at `130,314` gas; the eventual net saving is modeled at roughly `120,000–150,000` gas because a replacement must still read `canOwnerManage` and will change surrounding ABI/call costs.

Other major conclusions are:

1. Registered-payee accounting is expensive because it loads and rewrites an eight-field `PayeeData` structure. It costs approximately `235,890` gas on first use and `93,490` gas on repeat use.
2. Manager post-transfer accounting costs approximately `132,253` gas on first use and `24,053` gas on repeat use.
3. A cheque is expensive twice: creation costs `714,824` direct-transaction-equivalent gas, and later payment costs another `485,198–743,389` depending on the caller path.
4. The existing atomic agent `createAndPayCheque` route is `18.7–33.1%` cheaper than the measured two-transaction cheque lifecycles; it is `26.0–33.1%` cheaper specifically versus the owner-paid and agent-paid lifecycles.
5. The existing agent batch route saved `284,269` gas, or `29.7%`, when executing two transfers.
6. A normal partial transfer prices the outgoing amount and then prices the remaining wallet balance again. The two `isBasicEarnVault` checks alone consumed `26,886` gas.
7. Deposit-points accounting is performed on every non-eject transfer and can become materially more expensive when blocks advance and points actually accrue.
8. Billing pulls are approximately `116,000` gas cheaper than equivalent owner pushes because Billing bypasses the large manager authorization structures earlier.
9. An exact-full native-token transfer currently reverts during asset deregistration. This is a correctness issue discovered during profiling and should be fixed independently of the optimization work.

The practical optimization order should be:

1. Fix exact-full native transfers and add regression coverage.
2. Add the owner authorization fast path.
3. Make basic-vault classification an O(1) lookup.
4. Use the existing batch and atomic-cheque routes wherever their semantics match the product action.
5. Introduce a compact transfer-specific authorization bundle.
6. Combine transfer and remaining-balance pricing for explicitly supported standard assets.
7. Pack high-frequency manager, payee, cheque, and points data in a new wallet/config version.
8. Build a true wallet-native batch and a non-persistent instant-cheque path.

Savings estimates in this report overlap. They must not be summed without remeasuring the combined implementation.

## 2. Scope and Questions Answered

This analysis answers the following questions:

- What is the complete on-chain path for a normal user-wallet transfer?
- Which subcalls and state transitions consume the most gas?
- How do whitelist, payee, cheque, manager, Billing, and agent paths compare?
- What is the difference between first-use and steady-state gas?
- How much does batching save today?
- How much does the atomic cheque path save today?
- Which optimizations are low-risk, and which require a new security model or storage layout?
- Which improvements can benefit existing wallets, and which require new wallet/config templates?
- Which costs are wallet execution costs versus Base L1-data or account-abstraction sponsorship costs?

The analysis focuses on successful payment execution. It is not a complete protocol security audit, token-compatibility audit, or production sponsorship-provider audit.

The baseline uses a conventional non-yield mock ERC20 and local price infrastructure. Yield tokens, rebasing tokens, fee-on-transfer tokens, proxy-token implementations such as production USDC, and production oracle paths may produce different results and should be benchmarked separately.

## 3. Measurement Methodology

### 3.1 Environment

Measurements were produced with the repository's Titanoboa/Py-EVM environment at commit `cce97d56b62f58c0c3eeddb8fc551d1723bf0fc3`.

The benchmark harness used:

- Fresh wallets for independent scenarios.
- Mock ERC20 and MockRipe pricing infrastructure.
- Registered asset and initialized Ledger points during setup unless the scenario explicitly tested an untracked asset.
- Py-EVM `PragueState`, using Prague/post-Cancun gas accounting.

No payment benchmark was run against a Base mainnet fork. The results should therefore be treated as controlled protocol-execution measurements, not production cost receipts.

### 3.2 Transaction-boundary normalization

Gas tools can substantially understate or distort costs when multiple test actions share warm accounts, warm storage, or dirty storage within one simulated transaction context. The final profiling harness corrected for this by:

1. Completing wallet and scenario setup before measurement.
2. Locking setup storage as prior-transaction state so EIP-2200 `SSTORE` pricing and refunds used the correct original values.
3. Clearing EIP-2929 account and storage access state before each independent measured transaction.
4. Clearing transient storage before each independent measured transaction.
5. Prewarming only the top-level transaction target and addresses `0x01–0x0a`, matching the harness's transaction/precompile assumptions.
6. Measuring the top-level mutating call and all child calls.
7. Retaining transaction-wide warmth only for the intentionally batched scenario.

This matters because a simple cumulative `boa.env.get_gas_used()` measurement after fixtures can make repeat calls appear cheaper for the wrong reasons. The current [`scripts/utils/capture_gas.py`](../../scripts/utils/capture_gas.py) is useful as a collection wrapper, but a permanent CI benchmark should explicitly enforce transaction boundaries and prior-state locking.

### 3.3 Reported gas definitions

The report uses four quantities:

- **Gross execution:** EVM contract execution before applying gas refunds and excluding transaction intrinsic gas.
- **Refund:** The raw EVM refund counter reported by the measured computation.
- **Intrinsic:** `21,000 + 4 × zero calldata bytes + 16 × nonzero calldata bytes` for the modeled direct call.
- **Receipt-like:** `gross execution + intrinsic - applicable refund`.

The receipt-like calculation was:

```text
pre_refund_gas = gross_execution + intrinsic
applicable_refund = min(refund_counter, pre_refund_gas / 5)
receipt_like_gas = pre_refund_gas - applicable_refund
```

The `/ 5` cap follows the post-London 20% maximum refund rule in [EIP-3529](https://eips.ethereum.org/EIPS/eip-3529).

This receipt-like number models a direct transaction to the measured entry point. It does **not** model the complete sponsored UserOperation envelope.

### 3.4 First versus repeat

In this report:

- **First** means the recipient token balance is zero and the relevant manager/payee period data is uninitialized.
- **Repeat** means the relevant state is already nonzero, but account and storage access is cold because it is a new transaction.
- **Full balance** means the transfer leaves the wallet with zero of that asset and triggers the deregistration path.
- **Untracked native** means the wallet has native value but does not yet have the asset registered in wallet accounting.

### 3.5 Deposit-points caveat

No block travel occurred between setup and the main first/repeat measurements. Consequently, `_getLatestDepositPoints` returned zero new accrued points, although the point structures and USD values were still read and written.

An older, unnormalized block-advanced probe indicated that this subsystem becomes more expensive when accrued points actually change. That probe did not use the final prior-state storage locking, so its numbers are intentionally excluded from the benchmark tables and optimization estimates. A permanent cross-block transaction-boundary benchmark is required before quantifying the production delta.

## 4. Core Transfer Flow

The primary entry point is [`UserWallet.transferFunds`](../../contracts/core/userWallet/UserWallet.vy#L144).

A successful normal payment follows this sequence:

1. `_validateCanTransfer` selects the resolved asset and the `TRANSFER` or `PAY_CHEQUE` action.
2. `_performPreActionTasks` asks `UserWalletConfig` to validate signer permissions and return the action bundle.
3. The wallet clamps the requested amount against native or ERC20 balance.
4. `Appraiser.updatePriceAndGetUsdValue` prices the outgoing amount.
5. The wallet validates the recipient as a whitelist recipient, registered payee, or cheque recipient.
6. The wallet executes native `send` or ERC20 `transfer`.
7. Manager limits are updated when the action bundle marks the signer as a manager.
8. The wallet reads the remaining asset balance.
9. The remaining balance is priced and `WalletAssetData` is updated, or the asset is deregistered when its balance reaches zero.
10. LootDistributor and Ledger update user and global deposit points.
11. The wallet emits `WalletAction`.

The most important observation is that step 6 is small relative to steps 2, 4, 5, and 7–10.

### 4.1 Signer branches

#### Owner

The owner does not bypass recipient rules. An owner payment must still target a whitelisted recipient, registered payee, or valid active cheque.

The owner authorization shortcut occurs inside [`Sentinel`](../../contracts/core/walletBackpack/Sentinel.vy#L102), but [`ActionDataProvider`](../../contracts/core/userWallet/ActionDataProvider.vy#L155) evaluates and retrieves the manager arguments before Sentinel is called. This eager evaluation creates the `130,314`-gas current three-getter burden described later. Only the scalar `canOwnerManage` from the global structure is required by the owner branch.

Owner payments do not perform manager post-accounting because the returned action bundle does not mark the owner as a manager.

#### Manager

Managers use the same general action bundle but must also satisfy:

- Manager activation and period timing.
- Transfer permission.
- Asset allowlists.
- Payee allowlists where applicable.
- Per-manager and global transfer limits.
- Post-transfer manager counters and totals.

Manager asset and payee checks can scan bounded arrays of up to 40 entries. Whitelisted recipients avoid the manager allowed-payee scan because ActionDataProvider rewrites the recipient for authorization purposes.

#### Billing

Billing receives a special early return in [`ActionDataProvider`](../../contracts/core/userWallet/ActionDataProvider.vy#L155). It therefore avoids the large manager settings and period-data getters. Recipient/payee/cheque validation still occurs inside the wallet/config path.

#### Agent

Agent calls add one or more layers before the wallet:

- `AgentSenderGeneric` or a signed sender endpoint.
- `AgentWrapper`.
- `UserWallet.transferFunds`.

Signed paths additionally perform message hashing, `ecrecover`, nonce validation/update, and signature-related calldata processing.

### 4.2 Recipient branches

#### Whitelisted recipient

This is the cheapest recipient class. Config checks the whitelist mapping, and Sentinel returns without persistent recipient-period writes. There is some duplicated whitelist work between signer authorization and recipient validation, but the second storage access is warm inside the transaction.

#### Registered payee

Config loads:

- Payee membership/index.
- Full `PayeeSettings`.
- Global payee settings.
- Eight-field `PayeeData`.

Sentinel validates activation, asset restrictions, cooldown/count limits, USD limits, and optional unit limits. A successful payment rewrites the full `PayeeData` structure at [`UserWalletConfig.vy`](../../contracts/core/userWallet/UserWalletConfig.vy#L516).

#### Cheque

Config loads:

- The recipient's full cheque.
- Global cheque settings, including allowed assets.
- Global cheque period data.
- Owner/signer manager membership.

Sentinel validates active status, unlock and expiry, exact asset and amount, asset allowlists, price, cheque value, manager permissions, cooldown, transaction counts, and USD limits.

Successful payment updates cheque period data, decrements active cheque count, and clears the stored cheque.

## 6. Steady Owner Transfer Hotspot Attribution

The repeat owner-to-whitelist ERC20 flow has `351,839` gross contract execution gas. Exclusive call-tree attribution identified the following major components:

| Component | Approximate gas | Share of 351,839 execution |
|---|---:|---:|
| Global manager settings getter | 58,201 | 16.5% |
| Signer-specific manager settings getter | 56,625 | 16.1% |
| `UserWallet.transferFunds` exclusive work | 41,421 | 11.8% |
| Two `VaultRegistry.isBasicEarnVault` calls | 26,886 | 7.6% |
| `ActionDataProvider` exclusive work | 26,541 | 7.5% |
| Sixteen UndyHq address lookups | 21,808 | 6.2% |
| Manager period data getter | 15,488 | 4.4% |
| Ledger points getter | 10,933 | 3.1% |
| Repeat ERC20 transfer | 10,194 | 2.9% |
| Ledger vault-token getter | 9,384 | 2.7% |
| Ledger points setter | 8,965 | 2.5% |
| Appraiser exclusive work | 7,955 | 2.3% |

These rows are exclusive call-tree components, but they should still be treated as diagnostic attribution rather than an additive optimization budget. Removing one call can change warmth, memory expansion, ABI encoding, and downstream exclusive costs.

The most important comparison is:

```text
Current three-getter owner burden: 130,314 gas
Actual repeat ERC20 transfer:       10,194 gas
Ratio:                               12.8×
```

The wallet spends almost thirteen times more gas on the current manager-data retrievals than it spends moving the token, even though the owner branch needs only the scalar `canOwnerManage` from those retrieved structures.

## 7. Root-Cause Analysis

### 7.1 Eager owner authorization arguments

[`ActionDataProvider.checkSignerPermissionsAndGetBundle`](../../contracts/core/userWallet/ActionDataProvider.vy#L139) retrieves manager period data, full manager settings, and full global manager settings before calling Sentinel.

[`Sentinel`](../../contracts/core/walletBackpack/Sentinel.vy#L102) then checks whether the signer is the wallet owner and whether owner management is enabled. If true, it returns without using the manager-specific structures.

This is a language/call-architecture issue rather than a subtle opcode issue: external-call arguments are evaluated before the callee can short-circuit. The owner branch needs the scalar `canOwnerManage`, but it does not need the rest of the global settings structure or either signer-specific manager structure.

The remedy must move the owner branch before those getters. Merely adding another early return inside Sentinel will not help.

### 7.2 Oversized generic action bundle

The generic action bundle includes approximately 20 fields and resolves registry addresses such as LegoBook, Ledger, MissionControl, Hatchery, LootDistributor, Appraiser, Billing, and VaultRegistry.

Normal transfers do not need every one of these fields. The bundle also causes large ABI encoding/decoding and memory work and contributes to repeated UndyHq lookups.

A transfer-specific bundle can be materially smaller and can avoid unrelated swap, Lego, liquidity, and deployment configuration.

### 7.3 Storage-heavy payee data

The payee flow retrieves and rewrites a full eight-field `PayeeData` structure. First use incurs multiple zero-to-nonzero storage transitions, explaining the `235,890`-gas first validation/write cost. Repeat updates are cheaper but remain approximately `93,490` gas.

Some values are needed for active on-chain limits. Others, such as lifetime transaction counters used only for analytics, are candidates for events or an indexer.

### 7.4 Storage-heavy manager data

Manager post-accounting reads settings and period state again and rewrites a seven-field `ManagerData` structure.

The first update costs approximately `132,253` gas because it initializes multiple storage words. Repeat updates cost approximately `24,053` gas.

### 7.5 Cheque persistence and double validation

Cheque creation persists a large cheque structure and updates cheque creation/accounting state. Payment later retrieves, validates, updates global paid-period data, decrements active count, and clears the stored cheque.

For delayed cheques, persistence is necessary. For a cheque created and paid atomically, storing a complete cheque is avoidable in principle.

The current atomic flow receives substantial same-transaction storage refunds, so its net cost is much lower than gross execution. Nevertheless, it still pays for multiple authorization, validation, pricing, accounting, and cross-contract passes. A dedicated instant path should target those duplicate passes, not merely the storage clear.

### 7.6 Duplicate pricing and vault detection

The wallet prices the outgoing amount before the transfer at [`UserWallet.vy`](../../contracts/core/userWallet/UserWallet.vy#L165). For a partial transfer, it later reads and prices the remaining balance at [`UserWallet.vy`](../../contracts/core/userWallet/UserWallet.vy#L1166).

Both Appraiser paths repeat configuration, authorization, oracle, and vault-classification work.

`VaultRegistry.isBasicEarnVault` loads a complete vault configuration to answer a Boolean question. The two calls consume `26,886` gas even for an ordinary non-vault ERC20.

### 7.7 Synchronous deposit-points accounting

Every non-eject transfer calls [`LootDistributor.updateDepositPointsWithNewValue`](../../contracts/core/LootDistributor.vy#L641), which reads user/global point structures and writes through Ledger.

This keeps rewards continuously synchronized but places reward-accounting cost on every payment, including the high-frequency transfer path Hightop sponsors.

### 7.8 Billing duplication

[`Billing._pullPayment`](../../contracts/core/Billing.vy#L207) checks ERC20 balance at least twice in the no-withdrawal case and then always attempts wallet asset deregistration at [`Billing.vy`](../../contracts/core/Billing.vy#L236), even when the transfer is partial.

The wallet subsequently performs its own balance and asset-accounting work. This is a smaller hotspot than owner authorization or payee storage, but it is a clear cleanup opportunity.

### 7.9 Untracked-asset churn

The untracked native scenario costs `506,800`, compared with `388,286` for a tracked native transfer to the same kind of empty recipient. The like-for-like `118,514`-gas difference includes asset registration and associated wallet/points initialization. Comparing against the `363,286` tracked transfer to an existing recipient produces a `143,514`-gas difference, but `25,000` of that is the unrelated native new-account charge.

Wallets that frequently empty, deregister, refill, and transfer a canonical payment asset can repeatedly pay this churn. A limited sticky-registration policy for ETH and selected payment tokens may be beneficial, but it increases the number of zero-balance assets retained for enumeration and accounting.

### 7.10 Agent signature duplication

The signed agent path hashes action data, performs `ecrecover`, validates and writes a nonce, emits nonce-related state/events, and carries larger outer calldata before reaching AgentWrapper and the wallet.

If the external sponsored account or session-key layer proves exactly the same authority and scope, Hightop may be paying for duplicate authentication. Removing a layer changes the security boundary and should only follow an explicit threat-model review.

## 8. Detailed Recommendations

The savings ranges below are measured where explicitly stated and modeled otherwise. They overlap.

### R1. Add an owner-specific authorization fast path

**Priority:** Highest  
**Affected flows:** Owner whitelist, owner payee, owner cheque  
**Expected saving:** Modeled `120,000–150,000` gas per owner payment  
**Evidence quality:** `130,314` current getter burden measured; replacement net saving not yet measured  
**Risk:** Medium; authorization-critical  
**Existing wallets:** Requires migration to a new wallet/config pair; deploying only a new Config or ActionDataProvider is insufficient

The flow should conceptually become:

```text
1. Preserve Billing-specific handling.
2. Preserve locked-signer validation.
3. If signer == walletOwner:
   a. Read only a scalar canOwnerManage value.
   b. Enforce owner authorization.
   c. Return the compact transfer data needed by UserWallet.
4. Only non-owner signers load manager period/settings structures.
```

Required invariants:

- Frozen-wallet behavior remains unchanged.
- Ejection-mode behavior remains unchanged.
- Locked-signers cannot gain access.
- `canOwnerManage` remains authoritative.
- Recipient whitelist/payee/cheque validation still runs.
- Billing's current special handling remains unchanged.

This should be validated through differential tests that execute the old and new authorization logic over the same generated owner/manager/settings states.

### R2. Make basic-vault classification O(1)

**Priority:** Very high  
**Affected flows:** Nearly every priced transfer  
**Expected saving:** Modeled approximately `20,000–25,000` gas per cold transfer  
**Evidence quality:** Current two-call cost of `26,886` measured; replacement mapping cost not yet measured  
**Risk:** Low to medium  
**Existing wallets:** Potentially, but only through a governed Appraiser/VaultRegistry upgrade with complete state migration and rotation

Maintain a dedicated mapping or bitset such as `isBasicEarnVault[address]`. Update it on every vault add, update, disable, and removal path.

For existing wallets, this is not a trivial registry swap. A new VaultRegistry requires complete migration of canonical vault configuration plus governed address rotation, or the fast flag must live behind a newly rotated Appraiser that preserves all existing pricing semantics.

The optimization is safe only if the Boolean is an invariant of the canonical vault configuration. Tests must prove that no registry mutation path can leave the Boolean stale.

### R3. Add a transfer-specific authorization API and compact bundle

**Priority:** High  
**Affected flows:** All direct wallet transfers  
**Expected saving:** Approximately `20,000–100,000` gas  
**Evidence quality:** Root-cause measurement plus modeled redesign  
**Risk:** Medium  
**Existing wallets:** Usually new templates/migration

The transfer bundle should contain only fields required for:

- Wallet and signer identity.
- Frozen/eject/locked state.
- Owner or manager classification.
- Transfer-specific permissions and counters.
- Recipient classification.
- Ledger/Appraiser/Loot/Billing addresses used by the transfer.

It should not retrieve unrelated Lego, swap, liquidity, or deployment data.

For manager allowed assets and payees, maintain O(1) membership mappings. Arrays may remain for enumeration, UI reads, and migration, but validation should not scan them.

### R4. Use existing batching immediately and design a wallet-native batch

**Priority:** High for multi-payment workloads  
**Affected flows:** Agent and future owner/manager multi-payment actions  
**Measured current saving:** `284,269` gas (`29.7%`) for two generic-agent transfers  
**Modeled future saving:** Approximately `100,000–250,000` for each additional transfer relative to the current separate-call architecture  
**Risk:** Medium to high for a new wallet-native batch

The measured `29.7%` is a local direct-transaction-equivalent execution result, not a measured reduction in complete production sponsored cost. The modeled per-additional-transfer range will shrink after other optimizations such as the owner fast path, compact bundle, and points redesign; it is not additive to them.

Immediate action:

- Route two or more compatible agent payments through the existing batch entry point.

Future wallet-native batch:

- Authenticate once.
- Group payments by asset.
- Price each asset once where safe.
- Update wallet asset data once per asset.
- Update deposit points once after final wallet value is known.

The batch must preserve per-payment semantics:

- Recipient/payee/cheque validation.
- Per-transaction count limits.
- Manager and payee cooldowns.
- Ordering and atomicity.
- Exact event/indexer behavior or an explicitly versioned replacement.

### R5. Use the atomic cheque route now and build a non-persistent instant cheque

**Priority:** High only when cheque semantics are already required for the one-off payment  
**Affected flows:** Cheques intended to be created and paid immediately  
**Measured current saving:** `224,423–482,614` gas depending on comparison path  
**Modeled dedicated-path saving:** Approximately `200,000–400,000` additional gas  
**Risk:** Medium product/security-semantic risk for selecting the existing route; high for a new dedicated path  
**Existing wallets:** Existing atomic route yes; dedicated new route generally requires new contracts/templates

Immediate action:

- Use `AgentWrapper.createAndPayCheque` only when cheque semantics are already required, the cheque is intended to execute immediately, and the agent/product authorization model is appropriate. Do not route an ordinary whitelist or payee payment through a cheque merely to pursue the lifecycle percentage saving.

Future action:

- Validate creation and payment rules in one function.
- Price once.
- Update every required creation and payment counter/last-block field once, with the same shared-period-reset semantics as the current two-stage lifecycle.
- Do not persist a full cheque that is never intended to survive the transaction.

The new path must preserve:

- Allowed asset rules.
- Manager cheque permissions.
- Allowed-payee rules where applicable.
- Creation-period limits.
- Paid-period limits.
- Both creation and paid counters and last-block fields.
- Shared creation/payment period-reset behavior.
- Creation and payment cooldowns.
- `instantUsdThreshold` eligibility and expensive-cheque delay behavior.
- Maximum-active-cheque semantics or an explicitly proven atomic equivalent.
- Nonzero price/value validation.
- Exact amount and asset.
- Locked/frozen/eject behavior.
- Replay prevention.

Delayed, locked-until-later, or expiring cheques should retain the persistent lifecycle.

An alternative future architecture is an EIP-712 one-time payment permit with a bitmap nonce. That can eliminate the persistent cheque but materially changes the authorization and recovery model and should be treated as a separate security project.

### R6. Pack manager, payee, and cheque period data

**Priority:** High for first-use payees/managers and cheque-heavy wallets  
**Affected flows:** Manager, payee, and cheque accounting  
**Expected saving:** Approximately `10,000–120,000`, depending on path and first/repeat state  
**Risk:** High storage-layout and overflow risk  
**Existing wallets:** Requires migration or new template

Current logical layouts include:

- `ManagerData`: seven fields/slots.
- `PayeeData`: eight fields/slots.
- `ChequeData`: eleven fields/slots.

Vyper does not automatically pack independent struct fields into a shared storage word. Use explicit packed words with documented and checked bounds.

Candidate widths:

- Block numbers and transaction counts: typically `uint64` with explicit maximums.
- USD and unit totals: checked `uint128` or `uint192`, selected from real protocol maximums rather than assumption.

Candidates for removal from on-chain storage include lifetime counters used only for analytics, such as `totalNumTxs` and cumulative cheque statistics that do not participate in validation. Emit events and reconstruct them in an indexer instead.

Before removal, run a complete read-site search to prove that no contract, migration, governance, or UI-critical view depends on the field.

### R7. Pack or redesign deposit-points accounting

**Priority:** Medium to high because it affects every transfer  
**Affected flows:** All non-eject transfers  
**Expected saving:** `10,000–25,000` conservatively; `25,000–70,000` with redesign  
**Risk:** High for reward correctness

Conservative changes:

- Pack `usdValue` with `lastUpdate` where numeric bounds allow.
- Avoid provable no-op same-block writes.
- Avoid rereading values already available from wallet post-accounting.

Aggressive changes:

- Use a global reward accumulator with lazy per-user settlement.
- Settle points only on balance-changing actions that actually cross an accrual boundary.
- Move some accounting to events plus Merkle or indexed claims.

Any redesign requires invariants around time, global totals, user entry/exit, rounding, and multiple actions in one block.

### R8. Combine outgoing and remaining-balance pricing

**Priority:** Medium to high  
**Affected flows:** Partial transfers of standard assets  
**Expected saving:** Approximately `10,000–30,000` gas  
**Risk:** Medium

For explicitly supported standard, non-rebasing, non-fee-on-transfer assets, a transfer-specific Appraiser endpoint can return:

- USD value of the transfer.
- USD value of the expected remaining balance.
- Yield classification.

from a single price/configuration observation.

Do not infer the post-transfer balance for arbitrary tokens. Retain an actual second `balanceOf` and conservative pricing path for:

- Fee-on-transfer tokens.
- Rebasing tokens.
- Yield wrappers with nonlinear price-per-share behavior.
- Tokens with callbacks or nonstandard balance behavior.

### R9. Remove duplicate Billing balance and deregistration work

**Priority:** Medium  
**Affected flows:** Billing payee and cheque pulls  
**Expected saving:** Approximately `5,000–15,000` gas  
**Risk:** Low to medium

For explicitly supported standard tokens:

- Cache the pre-transfer balance.
- Avoid the second Billing-level balance read when no withdrawal occurred.
- Do not call deregistration for a known partial payment.
- Pass known balance information to the wallet only if doing so cannot be forged and does not weaken token compatibility.

### R10. Consider sticky tracking for canonical payment assets

**Priority:** Data-dependent  
**Affected flows:** Wallets that frequently empty and refill ETH or a principal stablecoin  
**Observed like-for-like scenario delta:** Untracked native was `118,514` gas more expensive than tracked native when both recipients were empty  
**Risk:** Medium product/accounting tradeoff

Possible approaches:

- Never deregister native ETH from the wallet asset list.
- Retain selected canonical payment assets at zero balance.
- Register funded payment assets during the inbound/deposit flow rather than during the outbound payment.

Tradeoffs:

- Larger zero-balance asset lists.
- More expensive enumeration or full-wallet updates.
- Potential UI confusion unless zero balances are filtered.
- Need to keep wallet total USD and points at zero correctly.

This should be driven by production data showing how often users empty and later refill the same asset.

### R11. Consolidate duplicate agent authentication only after threat modeling

**Priority:** Medium  
**Affected flows:** Signed agent actions inside an already authenticated sponsored account/session  
**Expected saving:** Approximately `10,000–30,000` execution gas plus outer calldata bytes  
**Risk:** High security-boundary risk

If the ERC-4337 account or session key authenticates the same signer, wallet, action type, parameters, expiry, and nonce scope, the inner agent signature may duplicate work.

Before consolidation, document:

- Which key compromise each layer protects against.
- Domain separation.
- Replay domains and chain IDs.
- Session scope.
- Nonce ownership and cancellation.
- Server/agent key compromise behavior.

If both layers remain necessary, reduce encoding cost with fixed compact signature fields such as `(r, vs)` and packed nonce/expiry values rather than dynamic bytes where ABI compatibility permits. See [EIP-2098](https://eips.ethereum.org/EIPS/eip-2098).

### R12. Apply micro-optimizations only after structural work

**Priority:** Low  
**Expected saving:** Usually hundreds to a few thousand gas each

Candidates:

- Cache balances for explicitly supported standard assets.
- Avoid the third `balanceOf` call during known-zero deregistration.
- Reorder `_deregisterAsset` guards so cheap index/count checks happen before external token calls.
- Use the shortest generated Vyper `transferFunds` overload rather than sending default Boolean arguments explicitly.
- Consider a smaller transfer-specific event only if indexer compatibility can be versioned safely.

The existing `WalletAction` event and individual ABI/memory operations are not large enough to outrank authorization, storage, pricing, batching, or points work.

## 9. Cheque Refund Interpretation

Cheque deletion deserves careful interpretation because gross execution and paid gas differ substantially.

Measured refunds were:

- Existing cheque payment: `52,800` gas.
- Atomic create-and-pay: `218,900` gas.

Both were below the 20% refund cap for their measured pre-refund gas, so the refund was usable in these scenarios.

Consequences:

- Clearing the full cheque is not as expensive in net paid gas as gross `SSTORE` attribution suggests.
- Replacing a full clear with only `active = False` is not a first-tier fee optimization.
- A tombstone retains stale data and requires every reader and future recreation path to overwrite or ignore it correctly.
- The best instant-cheque optimization is to eliminate duplicate authorization/pricing/accounting and avoid persistence entirely, not merely to avoid clearing slots.

For delayed cheques, full clearing remains defensible for state hygiene and replay safety unless a separately audited versioned/tombstone design proves a material net benefit.

## 10. Native Full-Balance Correctness Finding

### Finding

Execution reaches the native send, then later reverts, atomically rolling back the transfer.

The same failure applies when `MAX_UINT256` is passed and clamped to the wallet's entire native balance.

### Root cause

After the transfer leaves a zero balance, post-accounting enters the zero-balance branch at [`UserWallet.vy`](../../contracts/core/userWallet/UserWallet.vy#L1149) and calls `_deregisterAsset`.

`_deregisterAsset` first executes an ERC20 `balanceOf` call at [`UserWallet.vy`](../../contracts/core/userWallet/UserWallet.vy#L1206), even when `_asset` is the native sentinel address. The sentinel has no ERC20 bytecode, so the empty return data fails ABI decoding before later early-return guards can run.

The existing native transfer test at [`tests/core/userWallet/test_user_wallet.py`](../../tests/core/userWallet/test_user_wallet.py#L129) transfers only half the native balance and does not enter this path.

### Recommended fix

Either:

1. Branch on the native sentinel and use `self.balance`, or
2. Pass the already-known zero post-transfer balance into an internal deregistration function and avoid another external balance query.

Also move cheap `numAssets`/index guards before any token external call where invariant ordering permits.

Because `UserWallet` instances are immutable blueprint deployments, this fix cannot patch an existing wallet in place. Existing wallets require migration to a corrected wallet/config pair. Until migration is available, the operational mitigation is to prevent exact-full native payments and leave a small native balance in the wallet; this is a temporary UX guard, not a contract fix.

### Required tests

- Exact explicit native balance transfer.
- `MAX_UINT256` clamped to the full native balance.
- Full native transfer when the asset is registered.
- Full native transfer when asset/accounting state is unusual but valid.
- Partial native transfer continues to retain the asset.
- Full ERC20 behavior remains unchanged.

## 11. Base and Sponsorship Cost Model

### 11.1 Base has two major transaction-cost components

Base documents every transaction as having:

- An L2 execution fee.
- An L1 security/data fee used to publish transaction data.

Base notes that the L1 component is typically larger. See [Base Network Fees](https://docs.base.org/base-chain/network-information/network-fees).

The wallet optimizations in this report primarily reduce **L2 execution gas**:

- Storage reads and writes.
- Cross-contract calls.
- Authorization.
- Pricing.
- Token execution.
- Logs.
- Points accounting.

Large internal structs and returndata do not directly add L1 calldata bytes. Only the outer transaction or UserOperation encoding is published as input data.

Optimizations such as compact signatures, shorter function overloads, smaller `callData`, and smaller `paymasterAndData` can reduce the L1-data component as well as pre-verification gas.

### 11.2 Current minimum Base fee reference

As of this report date, Base documents a Base Mainnet minimum L2 base fee of `0.005 gwei`, subject to periodic adjustment.

At that illustrative floor:

```text
L2 execution cost in ETH = gas_used × 0.005 gwei / 1e9
```

For an illustration using the full current three-getter burden—not a claim that every unit will be eliminated after the replacement scalar read:

```text
130,314 gas × 0.005 gwei = 651.57 gwei
                              = 0.00000065157 ETH
```

At the Base documentation's illustrative `$2,000/ETH`, this is approximately:

- `$0.00130` per payment.
- `$1,303` per million payments.

This is L2 execution only. Actual savings rise when the L2 gas price is above the floor and do not include any L1-data or operator changes.

### 11.3 Measuring Base L1 fees

Base exposes the GasPriceOracle predeploy at:

```text
0x420000000000000000000000000000000000000F
```

Relevant methods include:

- `getL1Fee(bytes)` for a fully serialized transaction.
- `getL1FeeUpperBound(uint256)` for a size-based upper bound.

See the [Base fee documentation](https://docs.base.org/base-chain/network-information/network-fees) and [Base execution-fee specification](https://docs.base.org/base-chain/specs/protocol/execution/index).

### 11.4 The external sponsorship layer is not in this repository

The contract named [`Paymaster.vy`](../../contracts/core/walletBackpack/Paymaster.vy#L10) is the wallet's payee-management module. It is not the external ERC-4337 gas paymaster.

The full Hightop-sponsored cost may additionally contain:

- Account `validateUserOp` execution.
- Paymaster validation.
- Paymaster `postOp`.
- `preVerificationGas`.
- EntryPoint overhead.
- Bundler/operator surcharge.
- Outer UserOperation signature and calldata.
- Base L1-data fee.

These components require production UserOperation receipts and traces. See [ERC-4337](https://eips.ethereum.org/EIPS/eip-4337).

### 11.5 Recommended business KPI

Track:

```text
sponsored_cost =
    execution reimbursement
  + allocated Base L1 transaction fee
  + bundler/provider surcharge
```

If the provider invoice already bundles the Base L1 fee or surcharge into a single charged amount, use the invoiced components instead and do not double count them. ERC-4337 `actualGasCost`/reimbursement fields and provider billing conventions must be reconciled against the bundler's outer Base transaction.

Break it into:

```text
L2 wallet execution
+ L2 account/paymaster/EntryPoint execution
+ L1 data/security fee
+ operator surcharge
```

Report median, p90/p95, and total dollars per million payments for every major flow class.

## 14. Security and Correctness Test Gates

Every authorization or accounting optimization must preserve the following behavior.

### 14.1 Owner and signer invariants

- Frozen wallet cannot perform prohibited transfers.
- Ejection mode remains authoritative.
- Locked signer remains blocked.
- Owner requires the same `canOwnerManage` state as before.
- Owner cannot bypass recipient classification or limits.
- Billing bypass applies only to the registered Billing address.

### 14.2 Manager invariants

- Manager activation timing.
- Allowed assets.
- Allowed payees.
- Transfer permission.
- Cooldown.
- Per-period transaction count.
- Per-transaction, per-period, and lifetime USD limits applicable to manager transfers.
- Global manager limits.
- Correct behavior at period boundaries.

### 14.3 Payee invariants

- Activation block.
- Allowed asset.
- Cooldown/count limits.
- Specific and global USD limits.
- Unit limits.
- First-payment and period-reset behavior.

### 14.4 Cheque invariants

- Active status.
- Unlock and expiry.
- Exact asset and amount.
- Allowed asset.
- Maximum value and nonzero price.
- Manager create/pay permissions.
- Creation and paid-period limits.
- Single-use/replay protection.
- Cancellation behavior.

### 14.5 Token and pricing invariants

- Standard ERC20.
- Proxy stablecoin used in production.
- Native asset.
- Full-balance transfer.
- Yield asset.
- Rebasing or fee-on-transfer tokens if supported.
- Zero, stale, or changing prices according to protocol policy.
- Correct post-transfer wallet USD total.

### 14.6 Points invariants

- Same-block multiple actions.
- Multiple-block accrual.
- Full asset exit.
- Asset re-entry.
- User/global point conservation or the protocol's intended relationship.
- Rounding bounds.

### 14.7 Differential testing

For new fast paths, generate identical action/settings state and execute both:

- The current generic logic in a reference deployment.
- The proposed specialized logic in a candidate deployment.

Assert identical success/revert decisions, returned values, storage deltas, and emitted semantic events.

## 15. Deployment and Bytecode Constraints

Wallet and Config instances are immutable blueprint deployments through [`Hatchery`](../../contracts/core/Hatchery.vy#L232). Each wallet stores its paired Config address during construction at [`UserWallet.vy`](../../contracts/core/userWallet/UserWallet.vy#L116), and `ACTION_DATA_PROVIDER` is captured immutably by each Config at [`UserWalletConfig.vy`](../../contracts/core/userWallet/UserWalletConfig.vy#L144).

Consequences:

- Owner fast paths affect future wallet/config templates; existing wallets require migration to a new paired wallet and Config. Deploying only a new Config or ActionDataProvider does not update the pinned pair.
- Packed storage requires a new layout and migration.
- Wallet-native batching requires a new wallet template.
- A dedicated instant-cheque entry point generally requires new templates/contracts.
- Global Appraiser/VaultRegistry changes are the best candidates to benefit existing wallets, but require governed rotation and complete preservation or migration of registry state; an Appraiser-side fast flag may reduce the migration surface.
- Billing changes may benefit existing wallets if the Billing address is globally resolved and can be rotated safely.

### 15.1 Runtime size

A separate Vyper `0.4.3` compiler probe, distinct from the transaction-boundary gas harness, measured the current code-size-optimized UserWallet runtime at `23,032` bytes against the EIP-170 limit of `24,576`, leaving `1,544` bytes of headroom.

For the comparison build, the temporary compiler input removed only `# pragma optimize codesize` and compiled with `vyper -p . -O gas -f bytecode_runtime`:

- UserWallet gas-optimized runtime: `23,883` bytes, leaving `693` bytes.
- AgentSenderGeneric gas-optimized runtime: `25,255` bytes, exceeding EIP-170 by `679` bytes.

These bytecode figures are compiler outputs, not transaction-gas artifacts.

Therefore:

- Do not begin with a blanket compiler switch from code-size to gas optimization.
- Prefer deleting/replacing generic machinery before adding new branches.
- Consider helper-contract placement for new logic, while accounting for extra external-call gas.
- Enforce bytecode-size gates in CI for every optimization PR.

See [EIP-170](https://eips.ethereum.org/EIPS/eip-170).

## 16. What Not to Optimize First

The following are real but secondary:

- `WalletAction` event fields.
- A single redundant registry getter.
- One or two memory copies.
- Individual Boolean ABI fields.
- Cheque tombstoning without redesigning the lifecycle.
- Blanket compiler optimization changes.

These do not approach the value of:

- Replacing the `130,314`-gas current owner-path manager retrieval burden with a scalar fast path.
- Avoiding large payee/manager first-use storage writes.
- Batching multiple transfers.
- Avoiding a two-transaction cheque lifecycle.
- Reducing duplicate pricing and points work.

Micro-optimization should happen after the call graph and state model are simplified.

## 18. Final Assessment

The current payment design is expensive because it is highly defensive and keeps many subsystems synchronized on every transfer. The core transfer instruction is already cheap; the surrounding general-purpose authorization and accounting architecture is the optimization opportunity.

For Hightop's sponsored high-frequency payments, the highest-confidence path is:

1. Remove unused owner manager lookups.
2. Make vault classification O(1).
3. Batch compatible transfers.
4. Use atomic cheques for immediate one-off payments.
5. Create a compact transfer-specific path rather than continuing to optimize the generic action bundle around the edges.

Those changes attack the largest measured costs while preserving the existing payment categories. Storage packing, reward redesign, and non-persistent one-off authorization can provide further savings, but they carry substantially greater migration and security risk.

The next engineering artifact should be a permanent transaction-boundary gas benchmark suite. It should be paired with production Base UserOperation telemetry so Hightop optimizes the frequency-weighted sponsored dollar cost, not only local EVM gas in isolation.
