**Scope:** `UserWallet.transferFunds` — one-off payments, whitelist transfers, payee payments, digital cheques, and the agent entry path. Hightop sponsors all user gas, so the goal is to find where the gas goes and how to reduce it.

## 1. Executive summary

**A sponsored payment costs ~335k–650k gas of execution, of which the actual token transfer is ~24.5k first-touch / ~4.6k steady-state — roughly 6% cold and 1.4% warm. Everything else is protocol machinery.** The overhead is dominated by five things, all fixable to different degrees:

| # | Culprit | Measured cost | Runs on |
|---|---|---:|---|
| 1 | Manager-config struct reads inside the permission bundle (`managerSettings` + `globalManagerSettings` + `managerPeriodData`) | **~130k cold / ~13k warm** | **Every transfer, including owner-signed** |
| 2 | Payee validation: full-struct reads + 8-slot `PayeeData` rewrite | ~236k first payment / ~80k repeat | Every payee payment |
| 3 | `checkManagerLimitsPostTx`: re-reads manager structs + 7-slot `ManagerData` write | ~132k first / ~24k repeat | Every manager/agent transfer |
| 4 | LootDistributor deposit-points update (6 nested calls, 6 SLOAD + 6 SSTORE in Ledger) | ~60k cold / ~20k warm / ~99k first-ever | Every action, unconditionally |
| 5 | Appraiser called twice per transfer; `VaultRegistry.isBasicEarnVault` (11-slot struct) read both times; ~16 registry `getAddr` staticcalls per tx | ~61k + ~22k | Every transfer |

The single strongest finding: **the permission pre-check unconditionally loads ~27-slot manager settings structs as call arguments to Sentinel, even when the signer is the owner** — and Sentinel's owner path needs exactly one field (`canOwnerManage`) before returning early. That is ~130k of cold SLOADs on every owner-signed transfer for data that is never used.

Realistic impact of the recommended work (details in §8):

- **Quick wins (no storage migration):** owner→whitelist transfer drops from ~395k to roughly **~230k** (-40%); agent transfers save the same plus post-tx dedup.
- **With struct packing (new wallet/config version):** payee payments from ~412k warm to roughly **~250k**; first-payment cliff roughly halves.
- **Cheque lifecycle:** ~1.2M net gas per one-off cheque payment today; an instant-pay short-circuit that never persists the cheque saves ~300–400k of that.
- **Batching (already shipped):** two agent transfers in one `performBatchActions` measured **~28% cheaper** than two separate transactions. This is free savings available to the Hightop backend today.

Savings estimates overlap — do not sum them without re-measuring a combined implementation.

## 2. Methodology

### 2.1 How the numbers were produced

Measurements were taken with the repo's titanoboa/py-evm test environment (local fork, mock tokens, `MockRipe` pricing), using two harnesses that lived at `tests/_gas_profile_scratch.py` and `tests/_gas_analysis_probe.py` (since removed from the working tree; §10 describes how to reproduce):

- **Scenario harness** (`_gas_profile_scratch.py`): ran a scenario matrix (owner/manager/agent × whitelist/payee/cheque, first vs repeat, batch vs separate) and emitted a JSON report per scenario: gross execution gas, refund counter, a direct-transaction-equivalent figure (adds `21,000 + 4·zero + 16·nonzero` calldata intrinsic, applies the EIP-3529 refund cap), a per-component exclusive-gas breakdown aggregated over the call tree, and hot-line profiles.
- **Cold-tx probe** (`_gas_analysis_probe.py`): reset the EIP-2929 warm-access journal before each measured call so that "first" numbers reflect a genuinely cold transaction, and printed the full child-computation tree (per-call gas per contract).

Cross-checks: the two harnesses agree on repeat/warm numbers to within noise; the probe's cold numbers are ~10–15% above the scenario harness's "first" numbers (which run in a warmer environment), as expected. Every major measured claim below was also verified against a manual line-by-line trace of the contracts (storage slots touched, external calls made).

### 2.2 What the numbers mean

- **Execution gas**: EVM execution of the top-level call, before refunds, excluding tx intrinsic. This is the number quoted unless stated otherwise.
- **Tx-equivalent**: execution + modeled intrinsic/calldata, with the refund cap applied. Closest to a real receipt for a direct EOA call.
- Refunds matter for cheques and full-balance transfers (storage zeroing): quoted as "gross → net".

### 2.3 Caveats

- **Local mocks**: `MockRipe.getUsdValue` costs ~5.1k cold. The production Ripe price desk (real oracle reads) will cost more, so mainnet totals skew somewhat higher than these figures — the *relative* ranking of culprits is unaffected.
- The mock ERC-20 is a plain Vyper token (~24.5k cold transfer). Production USDC on Base is a proxy (adds a delegatecall + cold implementation account, roughly +5k).
- Measured on py-evm Prague semantics; Base is currently equivalent for the opcodes involved.
- On Base, total sponsored cost = L2 execution (dominant at these gas levels) + L1 data fee (small post-4844, but nonzero — see §8.6 on calldata).
- Scenario variance: payee "first" numbers vary a few % run-to-run with block advancement (points accrual, period windows). Ranges are given where observed.
- **Cheque "pay existing" refunds are overstated here.** This harness created the cheque in the same execution context as the payment, so zeroing the 11 cheque slots earned same-transaction refund treatment (218,900 counter). The codex report locks setup state as a prior transaction and measures a 52,800 refund → ~602,758 net for owner pay-existing; that figure is more representative whenever the cheque was created in an earlier transaction. The **atomic create-and-pay** numbers are unaffected (create and zero genuinely share one tx; both reports measure ~973–976k net).

## 3. Anatomy of a transfer

`UserWallet.transferFunds(recipient, asset, amount, isCheque, isSpecialTx)` (`contracts/core/userWallet/UserWallet.vy:146`) executes six phases:

```
1. PRE-ACTION      _performPreActionTasks (UserWallet.vy:978)
                   └─ UserWalletConfig.checkSignerPermissionsAndGetBundle   [view]
                      └─ ActionDataProvider.checkSignerPermissionsAndGetBundle
                         ├─ 8× UndyHq.getAddr (ledger, MC, legoBook, hatchery,
                         │     lootDist, appraiser, billing, vaultRegistry)
                         ├─ Ledger.getLastTotalUsdValue
                         ├─ 5× back-calls into UserWalletConfig (wallet, owner,
                         │     inEjectMode, isFrozen, indexOfManager)
                         ├─ MissionControl.isLockedSigner
                         ├─ UserWalletConfig.indexOfWhitelist(recipient)
                         ├─ UserWalletConfig.managerPeriodData(signer)      ← 7 slots
                         ├─ UserWalletConfig.managerSettings(signer)        ← ~27 slots
                         ├─ UserWalletConfig.globalManagerSettings()        ← ~27 slots
                         └─ Sentinel.canSignerPerformActionWithConfig       [pure logic]
                   └─ yield check per asset (skipped for non-yield assets)
2. AMOUNT + PRICE  IERC20.balanceOf(self)
                   Appraiser.updatePriceAndGetUsdValue(asset, amount)       [call #1]
                   ├─ UndyHq.getAddr(ledger) + Ledger.isUserWallet
                   ├─ MissionControl.getAssetUsdValueConfig ─ Ledger.vaultTokens (4 slots)
                   ├─ RipePriceDesk.getUsdValue (via RipeHq.getAddr)
                   └─ UndyHq.getAddr(vaultRegistry) + VaultRegistry.isBasicEarnVault (11 slots)
3. RECIPIENT CHECK UserWalletConfig.checkRecipientLimitsAndUpdateData      [nonpayable]
                   ├─ whitelisted:  3 SLOADs, no writes                     (~3.2k)
                   └─ payee:        ~36 SLOADs + Sentinel.isValidPayeeAndGetData
                                    + 8-slot PayeeData rewrite              (~80–236k)
                   — or — UserWalletConfig.validateCheque for cheques       (~189k)
4. THE TRANSFER    IERC20.transfer / send()                                 (~4.6–24.5k)
5. POST-ACTION     _performPostActionTasks (UserWallet.vy:1020)
                   ├─ if manager: UserWalletConfig.checkManagerLimitsPostTx (~24–132k)
                   ├─ _updateAssetData: balanceOf + Appraiser call #2 + 4-slot
                   │    WalletAssetData write (+ deregistration if empty)
                   └─ LootDistributor.updateDepositPointsWithNewValue       (~20–99k)
                      └─ UndyHq.getAddr + Ledger.isUserWallet
                         + Ledger.getUserAndGlobalPoints (6 slots)
                         + Ledger.setUserAndGlobalPoints (6 slots + its own getAddr)
6. EVENT           log WalletAction
```

A plain whitelist transfer makes **~24 external call hops** across 8+ distinct contracts. Under EIP-2929, each newly touched contract costs 2,600 gas before it executes a single opcode; the first transfer in a tx touches ~9 cold accounts (~23k of pure account-access cost).

Two architecture facts that frame everything:

- **Vyper 0.4.x does not pack struct storage.** Every field — bools included — takes a full 32-byte slot, and copying a struct to/from storage touches every slot. Field count = SLOAD/SSTORE count. This multiplies every "read the settings struct" pattern below.
- **Wallets are full blueprint deployments, not proxies** (`Hatchery.vy:232,256`, `create_from_blueprint`). Per-call dispatch cost is zero (the right trade for a transfer-heavy product); the cost shows up once at wallet creation (~8–10M gas of code deposit for the two near-24KB templates, hence `pragma optimize codesize`). **Do not switch to minimal proxies** — that would add ~2.6k+ to every call to save one-time deploy gas.

## 5. Deep dives

### 5.1 The permission bundle — 53% of a whitelist transfer

`ActionDataProvider.checkSignerPermissionsAndGetBundle` (`contracts/core/userWallet/ActionDataProvider.vy:139-177`) does two jobs: assemble the 20-field `ActionData` bundle, and gate the signer. Both are overweight:

**Bundle assembly (~14 external staticcalls).** 8 registry `getAddr` calls, `Ledger.getLastTotalUsdValue`, and 5 back-calls into the very `UserWalletConfig` that just called it (`wallet()`, `owner()`, `inEjectMode()`, `isFrozen()`, `indexOfManager()`). Each back-call is a full external CALL round-trip for one or two SLOADs of data the config could have passed in.

**The manager-struct problem.** Lines 165-171 pass three storage structs *by value* as arguments to `Sentinel.canSignerPerformActionWithConfig`:

```vyper
assert staticcall Sentinel(_sentinel).canSignerPerformActionWithConfig(
    _signer == ad.walletOwner,
    ad.isManager,
    staticcall UserWalletConfig(_walletConfig).managerPeriodData(_signer),   # 7 slots
    staticcall UserWalletConfig(_walletConfig).managerSettings(_signer),     # ~26 slots + 3 DynArrays
    staticcall UserWalletConfig(_walletConfig).globalManagerSettings(),      # ~27 slots + arrays
    ...
)
```

These three getters are fetched **unconditionally** — but `Sentinel._canSignerPerformAction` (`Sentinel.vy:89-125`) returns `True` for the owner after checking a single bool (`globalManagerSettings.canOwnerManage`, line 103). Measured cost of the three getters: **130,314 cold** (58,201 + 56,625 + 15,488), ~13k warm. For a signer who isn't a manager (the owner), `managerSettings[owner]` is all-zero storage — and cold-SLOADing an empty slot still costs 2,100 each.

`ManagerSettings` / `GlobalManagerSettings` (`interfaces/WalletConfigStructs.vyi:210-231`) are ~26/27 fixed slots plus three bounded-40 DynArrays (`allowedAssets`, `allowedLegos`, `allowedPayees`). For a manager with populated allowlists these getters grow toward ~130 slots each. Manager-signed transfers therefore pay this cost *legitimately* pre-action — and then pay it **again** post-action (§5.3).

### 5.2 Recipient validation — whitelist is 10× cheaper than payee

`UserWalletConfig.checkRecipientLimitsAndUpdateData` (`UserWalletConfig.vy:474-516`):

- **Whitelisted recipient:** `indexOfWhitelist` lookup, empty structs, Sentinel returns immediately (`Sentinel.vy:478-479`), no writes. **~3.2k total.**
- **Registered payee:** full copies of `PayeeSettings` (15 slots), `GlobalPayeeSettings` (10 slots), `PayeeData` (8 slots) → ~36 SLOADs; Sentinel validates in memory; then the **entire 8-slot `PayeeData` is rewritten** (`:516`) though only ~6 fields change. First payment to a payee: the 8 slots go 0→nonzero at 20k each — that's the **235,890** exclusive figure. Repeat payments: ~80k.

Notes:

- `indexOfWhitelist[recipient]` is read **twice per transfer** in separate frames (ActionDataProvider `:162` and `checkRecipientLimitsAndUpdateData` `:484`).
- The Sentinel staticcall is made even for whitelisted recipients, carrying ~33 slots of empty struct calldata to get back an immediate `True`.
- `GlobalPayeeSettings` (10 slots) is re-read in full on every payee payment even though it's a rarely-changing singleton.
- Owner does **not** bypass recipient validation: normal transfers can only go to whitelisted addresses or registered payees regardless of signer (`Sentinel.vy:482-483`). Only `_isSpecialTx` (config-initiated migration/clawback) skips it.

**Payee record footprint:** ~25 slots (settings 15 + data 8 + two index mappings). **Whitelist record: 2 slots.** Registering a payee costs ~10× more storage than whitelisting, and every payment to it costs ~77k (warm) to ~236k (first) more.

### 5.3 Manager post-tx check — paying for the structs twice

For any manager/agent transfer, `_performPostActionTasks` calls `UserWalletConfig.checkManagerLimitsPostTx` (`UserWalletConfig.vy:426-466`), which **re-reads** `managerSettings` (~26 slots), `globalManagerSettings` (~27), and `managerPeriodData` (7) — the same structs the pre-check just loaded — then writes all 7 `ManagerData` slots back. Measured: **132,253** exclusive first time (the 7-slot period write goes 0→nonzero), ~24k repeat. Warm re-reads are "only" ~6k, but the round-trip, ABI-encoding of ~60 slots of struct data, and the full-struct write are recurring waste.

### 5.4 The cheque lifecycle — ~1.2M gas per one-off payment

Struct footprints (`interfaces/WalletConfigStructs.vyi:133-181`): `Cheque` 11 slots, `ChequeData` 11 slots, `ChequeSettings` ~16 slots + a bounded-40 `allowedAssets` array.

**Create** (`ChequeBook.vy:201-281`): `_getChequeConfig` makes **12 sequential staticcalls** into the wallet/config (including full reads of the 11-slot `ChequeData`, ~16-slot `ChequeSettings`, and 26-slot `managerSettings`); an Appraiser USD call; then `UserWalletConfig.createCheque` writes the 11-slot cheque + rewrites the 11-slot `ChequeData` + bumps `numActiveCheques` → **23 SSTOREs, ~344k in that frame alone**. Total ~692k.

**Pay** (`UserWalletConfig.validateCheque`, `:524-563`): re-reads cheque + settings + period data (~42 SLOADs), Sentinel validates in memory, then rewrites the 11-slot `ChequeData`, decrements `numActiveCheques`, and **zeroes all 11 cheque slots** → ~23 SSTOREs, partially refunded (218,900 refund counter, capped at 20% of tx gas). Total 583k gross → ~484k net.

Waste identified:

- `Cheque.recipient` duplicates the HashMap key — one dead slot per cheque.
- `Cheque.usdValueOnCreation` is written at creation but never read during validation (Sentinel uses the fresh `_txUsdValue`) — event-only data in storage.
- 3 bools + 3 block numbers each occupy full slots; hand-packed the struct is ~5 slots, not 11.
- `ChequeData`'s "created" half (5 fields) and "paid" half (5 fields) never change together, yet the full 11-slot struct is rewritten on both create and pay.
- USD value is priced twice (creation and payment) with two full Appraiser round-trips.

**Atomic create+pay** (`createAndPayCheque`) measured 973k net vs ~1.2M for the two-tx lifecycle — already ~19–26% better, and the natural place for a much bigger win (§8.3).

### 5.5 Pricing — two Appraiser round-trips that mostly repeat each other

The wallet calls the Appraiser twice per partial transfer: pre-transfer on the amount (`UserWallet.vy:166`) and post-transfer on the remaining balance (`:1166`). `Appraiser.vy` holds **no price cache** — despite the name, `updatePriceAndGetUsdValue` only writes a Ripe snapshot for basic-earn-vault assets; for USDC-type assets both calls are pure fan-out:

- `addys._getLedgerAddr()` — registry round-trip, **ignores the `ad.ledger` already resolved** (Appraiser.vy:278, and MissionControl re-resolves it again at MissionControl.vy:351 — the Ledger address is resolved 4× per transfer).
- `Ledger.isUserWallet` permission check ×2.
- `MissionControl.getAssetUsdValueConfig` ×2 → `Ledger.vaultTokens` (4 slots) ×2 — identical results.
- `RipePriceDesk.getUsdValue` ×2 (unit price is identical; only the amount differs).
- `VaultRegistry.isBasicEarnVault` ×2 — an **11-slot cold struct read (24,443 gas)** whose answer for a non-yield asset is always "no snapshot needed", *and which is already knowable* from the `isYieldAsset=False` the same call just computed. Measured 26,886 for the pair.

Full-balance transfers skip call #2 (balance is zero → deregister path), which is partly why full-balance ERC-20 transfers are cheaper net.

### 5.6 Deposit points — a fixed ~20–60k tax on every action

`_performPostActionTasks` ends with `LootDistributor.updateDepositPointsWithNewValue` (`UserWallet.vy:1052`) on every non-eject action, with no did-anything-change guard. The path (`LootDistributor.vy:641-688`): registry `getAddr` → `Ledger.isUserWallet` → `Ledger.getUserAndGlobalPoints` (6 slots) → compute → `Ledger.setUserAndGlobalPoints` (6 slots, and Ledger internally does *its own* registry `getAddr` + pause check). Six nested external calls, 6 SLOADs + 6 SSTOREs. Measured ~59.7k cold, ~19.9k warm, ~99k on a wallet's first-ever points write. All six slots genuinely change on a value-moving action (`usdValue`, `depositPoints`, `lastUpdate` × user and global), so the cost is design-inherent, not a bug — but the shape (two round-trips, re-resolved addresses, 3-slot unpacked structs) roughly doubles what the accounting strictly needs.

### 5.7 The agent entry path — modest per-call, big batch upside

Agents do **not** relay signatures into the wallet; the wallet sees `msg.sender = AgentWrapper` (a registered manager). Chain: EOA → `AgentSenderGeneric.transferFunds` (`AgentSenderGeneric.vy:93-104`) → `AgentWrapper.transferFunds` (`AgentWrapper.vy:104-113`) → wallet. Costs on top of a direct manager call:

- Hot-key path (backend holds an authorized key, empty signature): 2 extra hops + wrapper lookup + event ≈ **~13k**. Measured: 504,348 vs 491,428.
- Signature path: + expiry check, nonce SLOAD, 2× keccak, **ecrecover (3k)**, nonce SSTORE + `NonceIncremented` log ≈ **+28k**. Measured: 532,656.
- Any manager-path transfer (agent or not) also triggers the §5.3 post-tx check — that, not the entry hops, is the real agent premium.
- `performBatchActions` amortizes auth + warm state: 2 transfers = 631,153 vs 869,502 separate (**-27.4%**, and it also halves per-tx intrinsic + L1 data cost).

### 5.8 First-touch costs worth knowing

- First time a wallet holds an asset: `_registerAsset` + 4-slot `WalletAssetData` 0→nonzero + first points write ≈ **+165k** (untracked-ETH scenario: 518,979 vs 355,086 tracked).
- First payment to a payee: **+~140k** over repeat (8-slot `PayeeData` 0→nonzero).
- First manager action: **+~110k** over repeat (7-slot `ManagerData` 0→nonzero).
- Wallet creation itself: ~8–10M one-time (two full blueprint code deposits).

## 6. Struct storage footprints (why everything above is big)

Vyper 0.4.x allocates one full slot per struct field and copies whole structs on assignment. Field count = slot count = SLOAD/SSTORE count.

| Struct | Fields → slots | Read/written on | Ref |
|---|---|---|---|
| `ActionData` (memory bundle) | 20 | every action (assembled via ~14 calls) | `WalletStructs.vyi:37-57` |
| `ManagerSettings` | ~26 + 3 DynArrays (≤40 each) | every action ×2 for managers; ×1 wasted for owner | `WalletConfigStructs.vyi:210-219` |
| `GlobalManagerSettings` | ~27 + arrays | same | `:221-231` |
| `ManagerData` | 7 | written every manager action | `:201-208` |
| `PayeeSettings` | 15 | read every payee payment | `:34-45` |
| `GlobalPayeeSettings` | 10 | read every payee payment | `:47-55` |
| `PayeeData` | 8 | fully rewritten every payee payment | `:24-32` |
| `Cheque` | 11 | written at create, zeroed at pay | `:133-144` |
| `ChequeSettings` | ~16 + array | read at create and pay | `:146-162` |
| `ChequeData` | 11 | fully rewritten at create and at pay | `:170-181` |
| `PointsData` (user + global) | 3 + 3 | read+written every action | `Ledger.vy:34-47` |
| `WalletAssetData` | 4 | written every transfer | wallet storage |
| `VaultConfig` (isBasicEarnVault) | 11 | read 2× per transfer | `VaultRegistry.vy` |

Packing candidates: block numbers fit u48/u64, per-period counters fit u32, USD values fit u128, bools fit single bits. Hand-packing the four hottest structs (`PayeeData` 8→3, `ManagerData` 7→3, `ChequeData` 11→4, `PointsData` 3→2, `Cheque` 11→5) halves both the recurring write cost and the 20k-per-slot first-touch cliffs.

## 7. Redundancy catalog

## 8. Recommendations

Ordered by measured-impact-per-risk. Savings overlap; re-measure combinations.

### 8.1 Quick wins — no storage layout changes, benefits existing flows

**R1. Owner fast-path in the permission check.** In `ActionDataProvider.checkSignerPermissionsAndGetBundle`, when `_signer == ad.walletOwner`, read only `globalManagerSettings.canOwnerManage` (member access on a storage struct is a single SLOAD — expose a tiny getter on the config) and skip the three struct getters and the Sentinel call entirely. Sentinel's logic for this case is already a one-field early return (`Sentinel.vy:103`).
*Saves: ~115–130k cold / ~13k warm on every owner-signed action — the single largest lever in the protocol. Risk: low; semantics are unchanged (still gated on `canOwnerManage`, frozen/eject checks stay).*

**R2. Price once per transfer.** Have the Appraiser return the unit price (or have the wallet call a `getPriceAndYieldFlag` once), then compute both `txUsdValue` and the post-transfer balance value locally. Skip `VaultRegistry.isBasicEarnVault` when the asset config already says `isYieldAsset == False`.
*Saves: ~30–45k per transfer (second Appraiser round-trip ~10k warm; the two `isBasicEarnVault` reads 26.9k; one oracle call). Risk: low-medium; keep the snapshot write for yield assets.*

**R3. Trust the addresses already resolved.** The `ActionData` bundle already carries `ledger`, `missionControl`, `legoBook`, `vaultRegistry`. Appraiser re-resolves Ledger "because it cannot be passed in" — that trust decision costs 4-6 registry round-trips per transfer across Appraiser/MissionControl/LootDistributor/Ledger. If callers are restricted to registered wallets (already checked via `isUserWallet`), passing addresses through is safe. Alternatively cache registry addresses locally per contract with an explicit refresh hook.
*Saves: ~10–20k per transfer. Risk: low with the existing caller checks.*

**R4. Collapse the Ledger points round-trip.** Add `Ledger.accruePoints(user, newUsdValue)` that reads, computes (points math is trivial), and writes in one call — removing one external hop and the duplicate internal `getAddr`/pause check. Pass `ad.lootDistributor`/`ad.ledger` down.
*Saves: ~8–12k per transfer. Risk: low.*

**R5. Don't re-fetch manager structs post-tx.** The pre-action check already loaded them; return the needed fields (caps + period data) inside `ActionData` (it's a memory struct — adding fields costs only calldata/memory), so `checkManagerLimitsPostTx` needs only the period-data write.
*Saves: ~10–15k warm per manager/agent transfer + the encode/decode of ~60 slots. Risk: low.*

**R6. Skip the Sentinel hop for whitelisted recipients** — `checkRecipientLimitsAndUpdateData` can return before the staticcall when `indexOfWhitelist != 0`; and pass the whitelist answer from the pre-action check (it already looked it up) instead of re-reading.
*Saves: ~2–3k. Small, but free.*

### 8.2 Product/ops levers — available today, no code changes

**R7. Batch agent actions.** `performBatchActions` measured **-27.4%** for two transfers (one auth, one warm environment, one intrinsic). The Hightop backend should aggressively coalesce agent actions per wallet. Batching also divides the per-tx L1 data fee and any AA/sponsorship per-op overhead.

**R8. Prefer the hot-key agent path over per-call signatures** where key custody allows (saves ~15k: ecrecover + nonce SSTORE + log). Where signatures are needed, batch them (one signature per batch, not per action).

**R9. Whitelist trusted recipients instead of registering them as payees** when caps aren't needed (user's own linked accounts, verified recurring recipients). Measured: ~77k cheaper per warm payment, ~236k cheaper on first payment, and 2 storage slots instead of ~25. Payees should be reserved for counterparties that genuinely need onchain limits.

### 8.3 Medium-term — new wallet/config template version (storage migration)

**R10. Hand-pack the hot structs** (see §6): `PayeeData` 8→3 slots, `ManagerData` 7→3, `PointsData` 3→2, `Cheque` 11→5, `ChequeData` 11→4 (or split its create/pay halves). Vyper won't pack automatically — use explicit smaller-width fields sharing bit-packed uint256s with helper pack/unpack functions.
*Saves: payee repeat payments ~25k, payee first payments ~100k, manager actions ~20k/~80k, cheque lifecycle ~150k+. Risk: medium — new template + migration path; keep old wallets on old layout.*

**R11. Split the per-transfer read set out of `ManagerSettings`/`GlobalManagerSettings`.** The per-action check needs a handful of fields (caps, expiry, transfer perms); the three bounded-40 allowlists should live in their own mappings consulted only when relevant (`allowedPayees` only for non-whitelisted recipients, etc.).
*Saves: up to ~100k+ for managers with populated allowlists. Risk: medium.*

**R12. Instant-cheque short-circuit.** When a cheque is created and immediately payable (already the atomic `createAndPayCheque` flow, and any cheque under `instantUsdThreshold` with no delay), validate and pay without persisting: no 11-slot write, no 11-slot zeroing, one pricing call, single period-data update.
*Saves: ~300–400k of the ~973k atomic flow. Risk: medium — must keep events sufficient for audit/history, and preserve the review-window semantics for above-threshold cheques.*

**R13. Slim the cheque record itself** for cheques that must persist: drop `recipient` (map key), move `usdValueOnCreation` to the event, pack blocks/bools.
*Saves: ~120k+ per cheque lifecycle. Risk: low-medium, same migration caveat.*

### 8.4 Structural — bigger swings, evaluate after the above

**R14. Per-transaction context cache in transient storage.** The bundle (8 addresses + owner/frozen/eject/manager flags) is invariant within a tx. `UserWallet` already uses transient storage (`checkedYield`); caching the bundle there would make action 2..N in a batch nearly bundle-free and collapse the pre/post double-derivation. The batch measurement (§4.3) bounds the win: ~120k+ per additional action.

**R15. Rethink per-action points accrual.** Deposit points are rewards accounting; they don't need synchronous 6-slot writes on every payment. Options: accrue lazily on value-*changing* actions only (skip when `newTotalUsdValue == lastTotalUsdValue`), checkpoint on claim, or move global aggregation off the hot path. Bounded by ~20–60k per transfer.

**R16. A dedicated "simple transfer" entry point** that composes R1/R2/R6: owner-or-manager transfer of a non-yield asset to a whitelisted recipient touching the minimal set (permission fast-path, one price, transfer, asset data, points). Most Hightop payments fit this shape; a purpose-built path avoids paying for the generality of the 20-action framework on every $5 payment.

### 8.5 What NOT to do

- **Don't switch wallets to minimal proxies** to save deploy gas — it adds ~2.6k+ to every call forever; full blueprint copies are the right trade for a transfer-heavy product (§3).
- **Don't remove the approve/reset hygiene or post-action balance verification** for gas — they're cheap relative to the items above and security-load-bearing.
- **Don't sum the savings in this report** — R1/R5/R14 overlap heavily, R2/R3 share calls. Re-measure each combination.

### 8.6 Sponsorship cost framing

On Base, L2 execution dominates at these gas levels; the L1 data fee is small post-4844 but scales with calldata (another point for batching — the agent path re-encodes the full call twice across sender→wrapper→wallet). Illustrative: at a 0.01–0.05 gwei Base fee and ETH ≈ $3k, a 400k-gas transfer costs ~$0.012–0.06 of execution; at 1M sponsored payments/month that's ~$12k–60k/month, so the ~40% quick-win reduction is directly material, and packing compounds it. (Recompute with live basefee — Base fees are volatile.)

## 9. Correctness bug found during profiling (fix independently)

**Exact-full-balance native ETH transfers revert.** Verified on this commit with a minimal repro: partial native transfer succeeds; transferring the wallet's exact remaining ETH balance reverts.

Cause: when the post-transfer balance hits zero, `_updateAssetData` takes the deregister path and `_deregisterAsset` (`UserWallet.vy:1205-1206`) begins with `staticcall IERC20(_asset).balanceOf(self)` — executed against the ETH pseudo-address (`0xEeee…`), which has no code, so Vyper's return-data check reverts the whole transfer. ERC-20 full-balance transfers are fine (they have code); ETH only hits this when `canDeregister` is true (owner/non-special tx) and the asset was registered or the balance went to exactly zero.

Fix shape: in `_deregisterAsset`, branch on `_asset == ETH` and use `self.balance` (as `_updateAssetData` already does at `:1144-1145`), or pass the already-known zero balance in. Add regression tests: exact-full ETH transfer by owner, by manager, and via cheque. The codex report independently flags the same bug.

## 10. Reproducing these measurements

The throwaway harnesses were intentionally not kept in the tree. To re-measure:

1. **Scenario totals:** a pytest module using the standard fixtures (`user_wallet`, `user_wallet_config`, `alpha_token`, `mock_ripe`, `paymaster`, `cheque_book`, `starter_agent`, `starter_agent_sender`, `migrator`, `createPayeeSettings`, `createChequeSettings`). For each scenario, inside `boa.env.anchor()`: set price via `mock_ripe.setPrice`, fund the wallet, register the asset via `user_wallet_config.updateAssetData(0, asset, False, sender=switchboard_alpha.address)`, whitelist via `addWhitelistAddrViaMigrator` / add payee via `user_wallet_config.addPayee(recipient, settings, sender=paymaster.address)`, then measure `boa.env.get_gas_used()` deltas around the call.
2. **Per-call attribution:** after a call, walk `contract._computation.children` recursively — each child exposes `msg.code_address`, `get_gas_used()`, `get_gas_refund()`; map addresses to names with `boa.env.lookup_contract`. "Exclusive" gas = frame gas minus sum of children.
3. **Cold-tx realism:** boa shares py-evm's EIP-2929 warm-access journal across calls; reset it between measured transactions (clear `boa.env.evm.vm.state._account_db._journal_accessed_state._journal` current values) or treat all numbers as warm-ish.
4. **Line-level hotspots:** `boa.env.enable_gas_profiling()` + `boa.profiling.global_profile()` for per-line tables.
5. A permanent CI gas benchmark (tracked scenarios, regression thresholds) would make future optimization work verifiable — recommended as part of implementing §8.
