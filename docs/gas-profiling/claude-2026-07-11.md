## 1. Executive summary

**A simple sponsored payment costs ~385k gas of L2 execution at production steady state (cross-block, whitelisted recipient), ~390–630k on first use, ~482k steady to a payee, and up to ~780k for an agent's first payee payment — all before the AA/paymaster/L1 envelope. The actual token movement is ~27k first / ~10k steady: 3–7% of the total.** The overhead is dominated by five things, all addressable to different degrees:

| # | Culprit | Measured cost | Runs on |
|---|---|---:|---|
| 1 | Manager-config struct reads inside the permission bundle (`managerSettings` + `globalManagerSettings` + `managerPeriodData`) | **130,314 per transfer** | Every wallet-initiated transfer — owner, manager, agent (Billing pulls are the exception; they return early) |
| 2 | Payee validation: full-struct reads + 8-slot `PayeeData` rewrite | ~236k first payment / ~93k repeat | Every payee payment |
| 3 | `checkManagerLimitsPostTx`: re-reads manager structs + 7-slot `ManagerData` write | ~132k first / ~24k repeat | Every manager/agent transfer |
| 4 | LootDistributor deposit-points update (6 nested calls, 6 SLOAD + 6 SSTORE in Ledger) | ~40–60k per tx (~20k only within a batch) | Every action (skipped only in eject mode) |
| 5 | Appraiser called twice per partial transfer (once when the balance empties); `VaultRegistry.isBasicEarnVault` (11-slot struct) read each time; ~16 registry `getAddr` staticcalls per tx | ~26.9k + ~21.8k | Every transfer |

The single strongest finding: **the permission pre-check unconditionally loads ~27-slot manager settings structs as call arguments to Sentinel, even when the signer is the owner** — of which the owner path consults a single boolean (`canOwnerManage`) before returning. That is 130,314 gas on every owner-signed transfer (12.8× the steady-state token transfer it surrounds) for structs that are otherwise unused on that path. The fix has one real edge case — an owner who is also a registered manager — specified in R1.

Realistic impact of the recommended work (details in §8):

- **Template-level code changes (owner fast-path, price-once, appraiser de-duplication):** steady owner→whitelist payment from ~374k (same-block) / ~385k (cross-block) toward a directional target of **~220–250k** (the codex report independently models the same target). No storage-layout change, but existing wallets still require migration to new templates — each wallet pins its config and each config pins `ActionDataProvider` immutably (§8 preamble).
- **Struct packing (new storage layout):** payee and manager first-use cliffs roughly halve; recurring writes drop ~20–25k per payment.
- **Cheque lifecycle:** create-then-pay costs 1,317,582 first-use / 1,075,507 steady for a one-off payment; the existing atomic route is **26–36% cheaper on matched state** (975,599 first-use, 691,384 steady), and a non-persistent instant path could remove another ~200–400k.
- **Batching (already shipped, no code changes):** two agent transfers via `performBatchActions` measured **284,293 gas cheaper** than two separate steady-state transactions (−33.4%), and each additional batched action also amortizes the fixed per-transaction envelope (intrinsic, L1 data, AA overhead). Free savings for the Hightop backend today.

Savings estimates overlap — do not sum them without re-measuring a combined implementation.

## 2. Methodology

### 2.1 How the numbers were produced

All scenario totals in §4 come from the in-repo opt-in benchmark:

```
GAS_PROFILE=1 python3 -m pytest tests/gas_profiling/test_transfer_gas_profile.py -q -s
```

It must run standalone (a guard skips it if other tests are collected), prints a JSON report, asserts regression baselines (±2.5%) plus exact refund invariants, and exits 0.

boa executes calls in one rolling journal context, which silently leaks transaction-warm state between calls. The harness therefore inserts an explicit **transaction boundary before every measured call**:

1. `state.lock_changes()` — locks all prior storage as previous-transaction state, so EIP-2200/EIP-3529 SSTORE pricing and refunds are computed against correct originals (a slot written during setup and cleared during measurement refunds 4,800, not the same-tx 19,900; a repeat write costs 2,900+cold, not the dirty 100).
2. Clears the EIP-2929 warm account/slot journal — every measured call starts with a cold access list, as a real transaction does.
3. Clears transient storage.
4. Prewarms only what a real transaction warms: `tx.origin`, `tx.to`, and the precompile range.

These semantics were verified against a minimal contract before use (same-context clear: 19,900 refund; cross-boundary clear: 4,800; post-boundary update: 5,270; dirty update: 470 — matching mainnet EVM rules).

**Same-block vs cross-block.** Plain scenarios execute in the same block as their setup — matching the codex baseline for exact cross-report comparison, but meaning deposit points accrue zero and `lastUpdate`/`lastTxBlock`/period fields are rewritten to the same value (100-gas no-op writes). The `_crossblock` scenarios advance one block first, so those fields genuinely change (2,900 each) and points accrual arithmetic runs — the closer model of production steady state. Measured premium: **+11,468** (whitelist), **+14,268** (payee and agent) per transfer. Two qualifications: (a) the cross-block rows are *sequential observations on the evolved wallet*, not cloned-state A/B comparisons where only the block number changes — the premiums are internally consistent with per-slot arithmetic, but a controlled A/B on duplicated fresh state is the rigorous design (listed as a gap); (b) the cheque scenarios run after `set_live_cheque_settings` advances through the config timelock, so they sit in a later block than the earlier scenarios, and first-vs-steady cheque deltas can include small block-state effects alongside accounting initialization. Deeper multi-block accrual and period-rollover boundaries remain unmeasured (§10).

Component attribution (§4.2, §4.3): the large read-only components (struct getters, registry lookups, vault reads) come from a cold-access call-tree probe and independently match the codex attribution to the gas unit. Write-dependent component figures are stated at normalized (prior-transaction) pricing, credited to the codex trace where this harness has no per-component capture.

### 2.2 What the numbers mean

- **Gross execution**: EVM execution of the top-level call, before refunds, excluding tx intrinsic.
- **Raw refund counter**: the EVM refund counter; the applied refund is capped at 20% of pre-refund gas (EIP-3529) and the tables note where the cap binds.
- **Receipt-like**: gross + modeled intrinsic (`21,000 + 4·zero + 16·nonzero calldata bytes`) − applied refund. Closest to a real receipt for a direct EOA transaction. **Quoted by default.**
- None of these include the ERC-4337/sponsorship envelope (account validation, paymaster validation/postOp, preVerificationGas, bundler surcharge) or the Base L1 data fee (§8.6). The intrinsic model also omits Prague's EIP-7623 calldata floor — it never binds for these execution-heavy transactions.

### 2.3 Caveats

- **Local mocks**: `MockRipe.getUsdValue` costs ~5.1k cold. The production Ripe price desk (real oracle reads) will cost more, so mainnet totals skew somewhat higher — the *relative* ranking of culprits is unaffected. The mock ERC-20 is a plain Vyper token; production USDC on Base is a proxy (roughly +5k per transfer).
- **First vs repeat**: "first" means the recipient-side state is uninitialized (recipient token balance zero; payee/manager period data zero) while wallet-level state (points, asset registration) is primed during setup. "Steady" means everything initialized. Warm-state savings exist only *within* one transaction (batches) — every new transaction starts with cold access lists.
- **Manager-direct scenario**: impersonates the wrapper contract as top-level sender; the receipt-like figure models an EOA manager making the same call (real EOA managers are supported; contracts cannot be `tx.origin`).
- **Billing pulls are not measured** here; note they skip the §5.1 permission-bundle cost entirely (early return in `ActionDataProvider`) — the codex report measured them ~116k cheaper than equivalent owner pushes.

## 3. Anatomy of a transfer

`UserWallet.transferFunds(recipient, asset, amount, isCheque, isSpecialTx)` (`contracts/core/userWallet/UserWallet.vy:146`) executes six phases:

```
1. PRE-ACTION      _performPreActionTasks (UserWallet.vy:978)
                   └─ UserWalletConfig.checkSignerPermissionsAndGetBundle   [view]
                      └─ ActionDataProvider.checkSignerPermissionsAndGetBundle
                         ├─ 8× UndyHq.getAddr (ledger, MC, legoBook, hatchery,
                         │     lootDist, appraiser, billing, vaultRegistry)
                         ├─ Ledger.getLastTotalUsdValue
                         ├─ 5× back-calls into UserWalletConfig (wallet, owner,
                         │     inEjectMode, isFrozen, indexOfManager)
                         ├─ (Billing signer returns here — skips all of the below)
                         ├─ MissionControl.isLockedSigner
                         ├─ UserWalletConfig.indexOfWhitelist(recipient)
                         ├─ UserWalletConfig.managerPeriodData(signer)      ← 7 slots
                         ├─ UserWalletConfig.managerSettings(signer)        ← ~27 slots
                         ├─ UserWalletConfig.globalManagerSettings()        ← ~27 slots
                         └─ Sentinel.canSignerPerformActionWithConfig       [pure logic]
                   └─ yield check per asset (skipped for non-yield assets)
2. AMOUNT + PRICE  IERC20.balanceOf(self)
                   Appraiser.updatePriceAndGetUsdValue(asset, amount)       [call #1]
                   ├─ UndyHq.getAddr(ledger) + Ledger.isUserWallet
                   ├─ MissionControl.getAssetUsdValueConfig ─ Ledger.vaultTokens (4 slots)
                   ├─ RipePriceDesk.getUsdValue (via RipeHq.getAddr)
                   └─ UndyHq.getAddr(vaultRegistry) + VaultRegistry.isBasicEarnVault (11 slots)
3. RECIPIENT CHECK UserWalletConfig.checkRecipientLimitsAndUpdateData      [nonpayable]
                   ├─ whitelisted:  3 SLOADs, no writes                     (~3.2k)
                   └─ payee:        ~36 SLOADs + Sentinel.isValidPayeeAndGetData
                                    + 8-slot PayeeData rewrite              (~93–236k)
                   — or — UserWalletConfig.validateCheque for cheques
4. THE TRANSFER    IERC20.transfer / send()                                 (~10–27k)
5. POST-ACTION     _performPostActionTasks (UserWallet.vy:1020)
                   ├─ if manager: UserWalletConfig.checkManagerLimitsPostTx (~24–132k)
                   ├─ _updateAssetData: balanceOf + Appraiser call #2 + 4-slot
                   │    WalletAssetData write (+ deregistration if empty)
                   └─ LootDistributor.updateDepositPointsWithNewValue       (~40–60k)
                      └─ UndyHq.getAddr + Ledger.isUserWallet
                         + Ledger.getUserAndGlobalPoints (6 slots)
                         + Ledger.setUserAndGlobalPoints (6 slots + its own getAddr)
6. EVENT           log WalletAction
```

A plain whitelist transfer makes **~24 external call hops** across 8+ distinct contracts. Under EIP-2929, each newly touched contract costs 2,600 gas before it executes a single opcode, and every transaction starts cold — the hop structure is a recurring cost, not a first-time cost.

Two architecture facts that frame everything:

- **Vyper 0.4.x does not pack struct storage.** Every field — bools included — takes a full 32-byte slot, and copying a struct to/from storage touches every slot. Field count = SLOAD/SSTORE count. This multiplies every "read the settings struct" pattern below.
- **Wallets are full blueprint deployments, not proxies** (`Hatchery.vy:232,256`, `create_from_blueprint`). Per-call dispatch cost is zero (the right trade for a transfer-heavy product); the cost shows up once at wallet creation (~8–10M gas of code deposit). A compiler probe in the codex report measured the UserWallet runtime at 23,032 of the 24,576-byte EIP-170 limit — only ~1.5KB of headroom, which constrains how new fast-path branches can be added. **Do not switch to minimal proxies** — that would add ~2.6k+ to every call to save one-time deploy gas.

## 5. Deep dives

### 5.1 The permission bundle — over half of a whitelist transfer

`ActionDataProvider.checkSignerPermissionsAndGetBundle` (`contracts/core/userWallet/ActionDataProvider.vy:139-177`) does two jobs: assemble the 20-field `ActionData` bundle, and gate the signer. Both are overweight:

**Bundle assembly (~14 external staticcalls).** 8 registry `getAddr` calls, `Ledger.getLastTotalUsdValue`, and 5 back-calls into the very `UserWalletConfig` that just called it (`wallet()`, `owner()`, `inEjectMode()`, `isFrozen()`, `indexOfManager()`). Each back-call is a full external CALL round-trip for one or two SLOADs of data the config could have passed in. (Exception: when the signer is Billing, the function returns right after bundle assembly — Billing pulls skip the locked-signer check, the whitelist pre-read, the manager getters, and Sentinel entirely.)

**The manager-struct problem.** Lines 165-171 pass three storage structs *by value* as arguments to `Sentinel.canSignerPerformActionWithConfig`:

```vyper
assert staticcall Sentinel(_sentinel).canSignerPerformActionWithConfig(
    _signer == ad.walletOwner,
    ad.isManager,
    staticcall UserWalletConfig(_walletConfig).managerPeriodData(_signer),   # 7 slots
    staticcall UserWalletConfig(_walletConfig).managerSettings(_signer),     # ~26 slots + DynArrays
    staticcall UserWalletConfig(_walletConfig).globalManagerSettings(),      # ~27 slots + arrays
    ...
)
```

These getters are fetched **unconditionally** — but `Sentinel._canSignerPerformAction` (`Sentinel.vy:89-125`) uses only `globalConfig.canOwnerManage` before returning `True` on the owner path (`:102-103`). External-call arguments are evaluated before the callee can short-circuit, so the fix must branch *before* the getters — another early return inside Sentinel changes nothing. Measured cost: **130,314** (58,201 + 56,625 + 15,488), paid fresh in every transaction (the ~4.2k warm price exists only for a second action inside the same tx, i.e., batches).

Two subtleties the fast path must preserve (see R1): Sentinel's owner shortcut applies only when `canOwnerManage` is true — an owner with it disabled who is *also a registered manager* falls through to full manager authorization (`Sentinel.vy:105-123`); and `ad.isManager` is set independently of Sentinel, so an owner-who-is-manager still runs manager post-accounting.

`ManagerSettings` / `GlobalManagerSettings` (`interfaces/WalletConfigStructs.vyi:210-231`) are ~26/27 fixed slots plus DynArrays (`allowedAssets` ≤40, `allowedPayees` ≤40, `allowedLegos` ≤25). For a manager with populated allowlists these getters grow substantially. Manager-signed transfers pay this cost *legitimately* pre-action — and then pay it **again** post-action (§5.3).

### 5.2 Recipient validation — whitelist is far cheaper than payee (for push payments)

`UserWalletConfig.checkRecipientLimitsAndUpdateData` (`UserWalletConfig.vy:474-516`):

- **Whitelisted recipient:** `indexOfWhitelist` lookup, empty structs, Sentinel returns immediately (`Sentinel.vy:478-479`), no writes. **~3.2k total.**
- **Registered payee:** full copies of `PayeeSettings` (15 slots), `GlobalPayeeSettings` (10 slots), `PayeeData` (8 slots) → ~36 SLOADs; Sentinel validates in memory; then the **entire 8-slot `PayeeData` is rewritten** (`:516`). First payment: 8 slots go 0→nonzero with a primary asset, 6 of 8 without one (the unit counters stay zero — measured ~40k difference). Repeat payments: ~93k.

Notes:

- `indexOfWhitelist[recipient]` is read **twice per transfer** in separate frames (ActionDataProvider `:162` and `checkRecipientLimitsAndUpdateData` `:484`).
- The Sentinel staticcall is made even for whitelisted recipients, carrying ~33 slots of empty struct calldata to get back an immediate `True`.
- `GlobalPayeeSettings` (10 slots) is re-read in full on every payee payment even though it's a rarely-changing singleton.
- Owner does **not** bypass recipient validation: normal transfers can only go to whitelisted addresses or registered payees regardless of signer (`Sentinel.vy:482-483`). Only `_isSpecialTx` (config-initiated migration/clawback) skips it.
- **Whitelist and payee are not interchangeable roles.** Whitelisted recipients only receive *pushes*. Recipient-initiated pulls come in two distinct forms: payee pulls (require registered payee settings with `canPull` — the Billing flows) and cheque pulls (require a separate active cheque with `canBePulled` — no payee registration involved). The whitelist, payee, and active-cheque roles are mutually constrained per address. The cost comparison applies to owner/manager push payments only.

**Payee record footprint:** ~25 slots (settings 15 + data 8 + two index mappings). **Whitelist record: 2 slots.** Measured end to end: a steady payee push costs +87,848 (same-block) over a whitelisted one; the first payment costs +196k more.

### 5.3 Manager post-tx check — paying for the structs twice

For any manager/agent transfer, `_performPostActionTasks` calls `UserWalletConfig.checkManagerLimitsPostTx` (`UserWalletConfig.vy:426-466`), which **re-reads** `managerSettings` (~26 slots), `globalManagerSettings` (~27), and `managerPeriodData` (7) — the same structs the pre-check just loaded (warm within the tx, but the round-trip and ~60-slot ABI encode/decode recur) — then writes all 7 `ManagerData` slots back (six become nonzero on a first transfer; the swap counter stays zero). Measured: **132,253** exclusive first time, ~24,053 repeat.

### 5.4 The cheque lifecycle — 1.08–1.32M gas per one-off create-then-pay

Struct footprints (`interfaces/WalletConfigStructs.vyi:133-181`): `Cheque` 11 slots, `ChequeData` 11 slots, `ChequeSettings` ~16 slots + a bounded-40 `allowedAssets` array.

**Create — 714,824 first-use / 606,717 steady** (`ChequeBook.vy:201-281`): `_getChequeConfig` makes **12 sequential staticcalls** into the wallet/config (including full reads of the 11-slot `ChequeData`, ~16-slot `ChequeSettings`, and 26-slot `managerSettings`); an Appraiser USD call; then `UserWalletConfig.createCheque` writes the 11-slot cheque + rewrites the 11-slot `ChequeData` + bumps `numActiveCheques` → **23 SSTOREs, 344,268 in that frame alone** on first use.

**Pay (later transaction) — 602,758 first-use / 468,790 steady** (`UserWalletConfig.validateCheque`, `:524-563`): re-reads cheque + settings + period data (~42 SLOADs), Sentinel validates in memory, then rewrites the 11-slot `ChequeData`, decrements `numActiveCheques`, and zeroes the cheque. The measured 52,800 refund = 10 nonzero cheque fields (`canBePulled=False` is already zero in this scenario) + the `numActiveCheques` 1→0 transition, × 4,800 cross-transaction — cheques with different boolean values refund slightly differently. Either way, clearing is *not* where the money goes; the validation/accounting passes are.

**Atomic create-and-pay — 975,599 first-use / 691,384 steady** earns same-transaction refund treatment (raw counter 218,900 = the same 10 cheque fields + `numActiveCheques`, each set-and-cleared within one tx at 19,900; 172,846 applied under the 20% cap), making it **26.0% cheaper first-use and 35.7% cheaper steady, on matched cheque-accounting initialization class** (see §4.1 for the route caveats), than the two-transaction lifecycle. Implication: the win of a dedicated instant path is *not* avoiding the storage clear (refunds already largely neutralize that) — it's eliminating the duplicate authorization, pricing, and accounting passes and the persistence of a record that never needed to outlive the transaction.

Waste identified:

- `Cheque.recipient` duplicates the HashMap key — one dead slot per cheque.
- `Cheque.usdValueOnCreation` is never read during payment validation (Sentinel uses the fresh `_txUsdValue`); it is, however, read by `cancelCheque` to populate `ChequeCancelled.usdValue` (`ChequeBook.vy:607`) — so moving it off-chain changes observable event semantics and needs indexer versioning.
- 3 bools + 3 block numbers each occupy full slots; hand-packed the struct is ~5 slots, not 11.
- `ChequeData`'s "created" half (5 fields) and "paid" half (5 fields) never change together in normal operation, yet the full 11-slot struct is rewritten on both create and pay. (Caveat for a split layout: both halves *do* change together during a period reset, so the split must preserve the coordinated reset semantics.)
- USD value is priced twice (creation and payment) with two full Appraiser round-trips.

### 5.5 Pricing — two Appraiser round-trips that mostly repeat each other

The wallet calls the Appraiser twice per partial transfer: pre-transfer on the amount (`UserWallet.vy:166`) and post-transfer on the remaining balance (`:1166`). `Appraiser.vy` holds **no price cache** — despite the name, `updatePriceAndGetUsdValue` only writes a Ripe snapshot for basic-earn-vault assets; for USDC-type assets both calls are pure fan-out:

- `addys._getLedgerAddr()` — registry round-trip that deliberately ignores the `ad.ledger` already resolved (Appraiser.vy:278; MissionControl re-resolves it again at MissionControl.vy:351 — the Ledger address is resolved 4× per transfer).
- `Ledger.isUserWallet` permission check ×2.
- `MissionControl.getAssetUsdValueConfig` ×2 → `Ledger.vaultTokens` (4 slots) ×2 — identical results.
- `RipePriceDesk.getUsdValue` ×2 (unit price is identical; only the amount differs).
- `VaultRegistry.isBasicEarnVault` ×2 — an **11-slot cold struct read**, measured 26,886 for the pair. Note: `isYieldAsset` (from `Ledger.vaultTokens`) and `isBasicEarnVault` (from `VaultRegistry`) are **separate state with no enforced invariant between them**, so the safe optimization is an explicit O(1) flag maintained by VaultRegistry (R2), not inferring one from the other.

Full-balance transfers skip call #2 (balance is zero → deregister path), which is partly why full-balance transfers are cheaper net.

### 5.6 Deposit points — a fixed tax on every action

`_performPostActionTasks` ends with `LootDistributor.updateDepositPointsWithNewValue` (`UserWallet.vy:1052`) on every non-eject action, with no did-anything-change guard. The path (`LootDistributor.vy:641-688`): registry `getAddr` → `Ledger.isUserWallet` → `Ledger.getUserAndGlobalPoints` (6 slots) → compute → `Ledger.setUserAndGlobalPoints` (6 slots, and Ledger internally does *its own* registry `getAddr` + pause check). Six nested external calls, 6 SLOADs + 6 SSTOREs — roughly 40–45k steady per transaction, ~60k with fully cold state, ~20k only for a subsequent action inside the same transaction. The cross-block scenarios put a measured envelope around the same-block understatement (+11.5–14.3k per transfer across all touched period/points fields); deep multi-block accrual remains to be benchmarked.

### 5.7 The agent entry path — modest per-call, big batch upside

Agents do **not** relay signatures into the wallet; the wallet sees `msg.sender = AgentWrapper` (a registered manager). Chain: EOA → `AgentSenderGeneric.transferFunds` (`AgentSenderGeneric.vy:93-104`) → `AgentWrapper.transferFunds` (`AgentWrapper.vy:104-113`) → wallet. Costs on top of a direct manager call:

- Hot-key path (backend holds an authorized key, empty signature): 2 extra hops + wrapper lookup + event ≈ **~14k** measured (agent repeat 416,554 vs manager-direct steady 402,234 after normalizing for the fresh-recipient slot).
- Signature path: + expiry check, nonce SLOAD, 2× keccak, **ecrecover (3k)**, nonce SSTORE + `NonceIncremented` log, and larger calldata (which also raises intrinsic/L1-data cost) ≈ **+25–30k**.
- Any manager-path transfer (agent or not) also triggers the §5.3 post-tx check — that, not the entry hops, is the real agent premium.
- `performBatchActions` amortizes auth + warm state: two steady transfers = 565,915 vs 850,208 separate (**−284,293, −33.4%**), and each batched action divides the fixed per-transaction envelope (intrinsic, L1 data, AA overhead) across the batch. (Batching isn't the only envelope-collapser — the atomic create-and-pay cheque similarly replaces two transactions with one.)

### 5.8 First-touch and per-recipient costs worth knowing

- Sending native ETH to an address that has never held ETH: **+25,000 exactly** (EVM new-account charge; applies per fresh recipient, unavoidable at the protocol level).
- Starting to track an asset the wallet didn't hold: **+81,535** measured on a wallet already tracking another asset (+118,514 on fully fresh registration state per the codex report) — asset registration, 4-slot `WalletAssetData` init, first points contribution.
- First payment to a payee: **+~125k** over repeat (586,934 vs 461,687).
- First manager action: **+~125k** over repeat (541,748 vs 416,554).
- Wallet creation itself: ~8–10M one-time (two full blueprint code deposits).

## 8. Recommendations

Ordered by measured-impact-per-risk. Savings overlap; re-measure combinations.

**Deployment reality (applies to R1, R2's wallet-side half, R5, R6, R11–R14):** wallets and configs are immutable blueprint deployments; each wallet pins its config at construction (`UserWallet.vy:119`) and each config pins `ActionDataProvider` as an `immutable` (`UserWalletConfig.vy:144,187`). So even pure code changes ship as **new templates** and reach existing users only through wallet/config migration. "No storage-layout change" below means migration is mechanical, not that existing wallets benefit in place. Global singletons (Appraiser, VaultRegistry, LootDistributor, Ledger, Billing) are the exception — governed rotation there can benefit existing wallets, at the cost of registry/state migration for the rotated contract.

### 8.1 Template-level code changes (no storage-layout change)

**R1. Owner fast-path in the permission check.** Restructure `ActionDataProvider.checkSignerPermissionsAndGetBundle` so the owner branch runs *before* the manager getters are evaluated:

```text
keep Billing early-return and the locked-signer check as today
if signer == walletOwner and canOwnerManage:      # one-slot getter on config
    take the owner shortcut — skip managerPeriodData / managerSettings /
    globalManagerSettings and the Sentinel call
    (ad.isManager stays as computed — an owner who is also a registered
     manager still runs manager post-accounting)
else:
    full existing path — including the owner-with-canOwnerManage-disabled
    case, which must still fall through to manager authorization when the
    owner is also a registered manager (Sentinel.vy:102-123 semantics)
```

*Saves: measured burden is 130,314; net saving modeled ~120–150k on every owner-signed action — the single largest lever. Risk: medium (authorization-critical; needs differential tests over generated owner/manager/settings states asserting identical accept/reject decisions, including owner-is-manager and canOwnerManage-disabled cases, with frozen/eject/locked-signer behavior unchanged). Existing wallets: migration required.*

**R2. Price once per transfer — for explicitly supported standard assets.** Fetch the unit price once; derive both `txUsdValue` and the post-transfer balance value from it. For the vault-snapshot check, add an explicit **O(1) `isBasicEarnVault` flag** maintained by VaultRegistry on every vault add/update/disable/removal (do *not* infer it from `isYieldAsset` — separate state, no enforced invariant; §5.5).
*Saves: ~30–45k per transfer (price consolidation ~10–30k, wallet-side; vault flag ~20–25k, registry-side and can benefit existing wallets via governed rotation). Risk: medium — price consolidation is safe only for standard, non-rebasing, non-fee-on-transfer tokens; keep the second `balanceOf` + conservative path for everything else. The vault flag needs an invariant test that no registry mutation path leaves it stale.*

**R3. Reduce redundant address-resolution hops — carefully; smaller than it looks.** Measured reality: after the bundle warms UndyHq, later `getAddr` calls cost only ~363 each, while a consumer-local cache slot is a *cold* 2,100 at each transaction start — per-consumer storage caches can **lose** gas. What might work: (a) thread addresses through calldata where the callee can safely validate the caller instead of the address (the `MiniAddys` pattern already exists; Appraiser's refusal to trust `ad.ledger` is a deliberate security boundary — changing it needs a trust-model review, e.g. only honoring caller-supplied addresses from Ledger-verified user wallets); (b) storage-cache the 8 bundle lookups inside `ActionDataProvider` (8 cold local SLOADs ≈ 16.8k vs ~18.9k of lookup calls — only ~2k gross, before implementation overhead, and the currently-stateless provider would need governed initialization, rotation synchronization, and stale-address protection); (c) immutables only where redeploy-on-rotation is acceptable (note: provider immutables would couple address rotation to wallet migration — likely a bad trade).
*Saves: provisionally ~2–8k depending on option — not the 10–20k a naive SLOAD-vs-CALL count suggests, and option (b) may not clear its own overhead. Treat as a hypothesis; do not implement without a benchmark of the actual design. Risk: medium.*

**R4. Collapse the Ledger points round-trip.** Add `Ledger.accruePoints(user, newUsdValue)` that reads, computes, and writes in one call. Scope honestly: the read getter currently carries no auth/pause check, so the only clear elimination is one external getter round-trip plus the 6-slot ABI encode/decode each way — all six SLOADs, all six SSTOREs, the write-side LootDistributor authorization + Ledger pause check, and LootDistributor's own graceful pause handling must remain.
*Saves: ~2–5k per transfer (unmeasured — benchmark the implementation). Risk: medium-high — a new Ledger is protocol-global state requiring governed rotation with full state migration, not a drop-in.*

**R5. Don't re-fetch manager structs post-tx.** The pre-action check already loaded them; carry the needed fields (caps + period data) through `ActionData` (a memory struct — added fields cost only calldata/memory) so `checkManagerLimitsPostTx` needs only the period-data write.
*Saves: ~10–15k per manager/agent transfer + the encode/decode of ~60 slots. Risk: low-medium (stale-read window must be reasoned about). New template.*

**R6. Short-circuit the whitelist recipient path.** `checkRecipientLimitsAndUpdateData` can return before the Sentinel staticcall when its own fresh `indexOfWhitelist` lookup is nonzero. (Reusing the *pre-action* lookup's answer instead of re-reading is not obviously safe across the intervening external calls and the Billing path — keep the fresh read.)
*Saves: ~1.5–3k. Small, but free. New template.*

### 8.2 Product/ops levers — available today, no code changes

**R7. Batch agent actions.** `performBatchActions` measured **−284,293 (−33.4%)** for two steady transfers — one auth, one warm environment, and the fixed per-transaction envelope (intrinsic, L1 data, AA overhead) amortized across actions. The Hightop backend should aggressively coalesce agent actions per wallet.

**R8. Prefer the hot-key agent path over per-call signatures** where key custody allows (saves ~25–30k: ecrecover + nonce SSTORE + log + calldata). Where signatures are needed, batch them (one signature per batch). Any consolidation with the outer AA/session-key layer is a security-boundary change — threat-model first (which key compromise each layer protects against, replay domains, nonce ownership) before removing anything.

**R9. Whitelist trusted recipients instead of registering them as payees — for push payments.** Measured: ~88k cheaper per steady push, ~196k cheaper on the first, and 2 storage slots instead of ~25. Scope: this substitution only works for owner/manager-initiated pushes — recipient-initiated pulls (Billing, pull-enabled payees/cheques) require payee registration, a whitelisted address cannot pull, and an address can't hold both roles. Reserve payees for counterparties that need onchain limits or pull rights.

**R10. Route immediate one-off cheque payments through the atomic `createAndPayCheque`** — measured 26.0% (first-use) to 35.7% (steady) cheaper than the matched two-transaction lifecycle — but only where cheque semantics are actually required and immediate execution is intended; don't reroute ordinary whitelist/payee payments through cheques for the discount.

### 8.3 Medium-term — new storage layout (template + migration)

**R11. Hand-pack the hot structs** (see §6): `PayeeData` 8→3 slots, `ManagerData` 7→3, `PointsData` 3→2, `Cheque` 11→5, `ChequeData` 11→4 (or split its create/pay halves).
*Saves: ~20–25k per steady payee/manager payment; halves the ~125k first-use cliffs; ~150k+ per cheque lifecycle. Risk: high (layout + overflow bounds); needs checked widths derived from protocol maximums and full migration tooling.*

**R12. Split the per-transfer read set out of `ManagerSettings`/`GlobalManagerSettings`.** The per-action check needs a handful of fields (caps, expiry, transfer perms); the allowlists (assets ≤40, payees ≤40, legos ≤25) should live in O(1) membership mappings consulted only when relevant, with arrays retained for enumeration/UI.
*Saves: up to ~100k+ for managers with populated allowlists. Risk: medium.*

**R13. Instant-cheque short-circuit.** When a cheque is created and immediately payable, validate creation and payment rules in one pass, price once, update the creation *and* payment counters/period data with the same shared-period-reset semantics, and never persist the cheque record.
*Saves: ~200–400k beyond the atomic route (the win is eliminating duplicate authorization/pricing/accounting passes — refunds already neutralize most of the storage-clear cost, §5.4). Risk: **high** — must preserve `instantUsdThreshold` eligibility, expensive-cheque delays, cooldowns, max-active-cheque semantics, both counter sets, permissions, and replay protection. Treat as a dedicated design + audit. Delayed/expiring cheques keep the persistent lifecycle.*

**R14. Slim the persistent cheque record**: drop `recipient` (map key), pack blocks/bools. Moving `usdValueOnCreation` off-chain changes observable behavior — it currently populates `ChequeCancelled.usdValue` (`ChequeBook.vy:607`) — so pair it with versioned events and indexer coordination.
*Saves: ~120k+ per persisted-cheque lifecycle. Risk: medium, same migration caveat.*

### 8.4 Structural — bigger swings, evaluate after the above

**R15. Per-transaction context cache in transient storage — addresses and static config only, and not where the code currently runs.** A hard constraint first: the bundle is assembled via a STATICCALL chain (`UserWallet.vy:990` → config → `ActionDataProvider`), and `TSTORE` reverts in static context — so the cache cannot simply be added to ActionDataProvider. It would have to live in the wallet's own non-static frames (the wallet stores the returned addresses after the pre-action call, as it already does with transient `checkedYield`), or behind a new non-static preparation path, keyed by config + signer, with explicit invalidation design. Scope: protocol addresses and static config only; `lastTotalUsdValue`, manager/payee period data, counters, cooldowns, recipient classification, and locked-signer/security state change between batch actions and must stay live reads — cache canonical addresses, never authorization conclusions. Realistic effect: trims the repeated bundle-assembly hops for actions 2..N in a batch; note those repeat reads are already warm within the tx (the 58,201→4,201 `globalManagerSettings` figure is the cold-vs-warm struct-read bound, not this cache's saving), so the upside is the residual call/ABI overhead. Benchmark before building.

**R16. Rethink per-action points accrual.** Because `_getLatestDepositPoints` accrues lazily from `lastUpdate`, skipping the write when the wallet's USD value is unchanged *appears* arithmetic-safe (the next touch accrues over the full elapsed window at the same value) — but this must be proven as an invariant (rounding, user/global coupling, claim-path interactions, multiple same-block actions), not assumed; only a same-block no-op is trivially safe. Larger redesigns (global accumulator + lazy per-user settlement, event/indexer-based analytics) are a rewards-correctness project. Bounded by ~40–60k per transfer; the cross-block scenarios (§4.1) now provide the baseline for quantifying it.

**R17. A dedicated "simple transfer" entry point** composing R1/R2/R6: owner-or-manager transfer of a standard asset to a whitelisted recipient touching the minimal set (permission fast-path, one price, transfer, asset data, points). Most Hightop payments fit this shape. Constraint: UserWallet has ~1.5KB of bytecode headroom (§3), so this likely means *replacing* generic machinery or placing logic in a helper contract (costing one extra call) rather than adding branches.

### 8.5 What NOT to do

- **Don't switch wallets to minimal proxies** to save deploy gas — it adds ~2.6k+ to every call forever; full blueprint copies are the right trade for a transfer-heavy product (§3).
- **Don't flip the compiler to `-O gas`** — the codex compiler probe shows UserWallet would shrink headroom to ~693 bytes and AgentSenderGeneric would exceed EIP-170 outright.
- **Don't tombstone cheques (`active = False`) instead of clearing** — cross-tx refunds make full clearing cheap (52,800 back on 11 slots), and a tombstone creates stale-state hazards for every reader. The real instant-cheque win is R13, not the clear.
- **Don't remove the approve/reset hygiene or post-action balance verification** for gas — they're cheap relative to the items above and security-load-bearing.
- **Don't sum the savings in this report** — R1/R5/R15 overlap heavily, R2/R3 share calls. Re-measure each combination.

### 8.6 Sponsorship cost framing

A sponsored Hightop payment's true cost has several components this repo can't fully measure: L2 execution (what this report measures and optimizes), the Base L1 data fee (scales with the outer transaction/UserOperation bytes — Base's own docs note it is often the *larger* component for typical light transactions, though these 340–630k-gas payments are execution-heavy), and the ERC-4337 envelope (account validation, paymaster validation + `postOp`, `preVerificationGas`, bundler surcharge).

Practical guidance:

- Everything in §8.1–8.4 cuts the L2 execution term; batching (R7) is the only lever here that also amortizes the L1-data and AA-envelope terms across actions.
- Don't budget from an assumed fee split. Pull production UserOperation receipts and allocate: wallet-call gas vs envelope gas vs L1 fee (Base exposes `GasPriceOracle.getL1Fee` at `0x420000000000000000000000000000000000000F`) vs provider surcharge, then weight each optimization by flow frequency × per-flow saving × effective fee.
- For scale intuition only: at Base's documented 0.005 gwei minimum base fee, 130,314 gas (the R1 burden) ≈ 0.00000065 ETH per payment — roughly $1.3k per million payments at $2,000/ETH, several-fold more at elevated basefees, before L1/envelope costs.

## 9. Correctness bug found during profiling (fix independently)

**Exact-full-balance native ETH transfers revert.** Verified on this commit with a minimal repro: partial native transfer succeeds; transferring the wallet's exact remaining ETH balance (explicit amount or `MAX_UINT256`-clamped) reverts, rolling back the whole payment.

Cause: when the post-transfer balance hits zero, `_updateAssetData` takes the deregister path and `_deregisterAsset` (`UserWallet.vy:1205-1206`) begins with `staticcall IERC20(_asset).balanceOf(self)` — executed against the ETH pseudo-address, which has no code, so Vyper's return-data check reverts. ERC-20 full-balance transfers are unaffected.

Fix shape: branch on the native sentinel and use `self.balance` (as `_updateAssetData` already does at `:1144-1145`), or pass the already-known zero balance in; also consider moving the cheap `numAssets`/index guards ahead of any external token call. Because wallets are immutable blueprint deployments, existing wallets can't be patched — the fix lands in the next template, and until then the operational mitigation is to block exact-full native sends in product (leave dust). Regression tests: exact-full ETH by owner/manager/cheque, `MAX_UINT256` full-clamp, partial unchanged, ERC-20 full unchanged. The codex report independently found the same bug.

## 10. Reproducing these measurements

The benchmark is maintained in-repo, opt-in, standalone-only, self-checking, and exits cleanly:

```
GAS_PROFILE=1 python3 -m pytest tests/gas_profiling/test_transfer_gas_profile.py -q -s
```

It prints a JSON report (gross execution, raw refund counter, applied refund, modeled intrinsic, receipt-like) for every scenario in §4.1, then asserts regression baselines (±2.5% on twelve scenarios including the cross-block rows, steady cheque lifecycle, atomic route, and batch), exact refund invariants (52,800 cross-transaction cheque clears; atomic raw 218,900 / applied 172,846), and the batch saving (284,293 ±2.5%). Design notes:

- Each measured call is preceded by a **transaction boundary**: `state.lock_changes()` (EIP-2200/3529 originals), EIP-2929 access-journal reset, transient-storage clear, and prewarming of `tx.origin`/`tx.to`/precompiles only (the full Prague precompile range 0x01–0x11; none are hit by these paths).
- `lock_changes()` flattens boa's snapshot journal, so the module is marked `ignore_isolation`, runs forward-only (scenario order matters — the agent's first manager action must stay first), skips itself unless it is the *only* collected test, and neutralizes leftover session-fixture anchor reverts on exit (a global revert no-op — acceptable only because the process is disposable and about to exit) so the run finishes green.
- Cross-block scenarios advance one block before measuring; same-block scenarios are retained as the codex-reconciled baseline. As noted in §2.1, cross-block rows are sequential evolved-state observations, not cloned-state A/B.
- Known gaps to extend it with: controlled same-block/cross-block A/B on duplicated fresh wallets, deep multi-block points accrual and period-rollover boundaries, a Base-fork run with production USDC + real Ripe pricing, the signed-agent path, Billing pulls, exact-full-native regression scenarios (to land with the §9 bug fix), and CI wiring if regression gating is wanted on every PR.

For component-level attribution (which call costs what inside a scenario), walk `contract._computation.children` recursively — each child exposes `msg.code_address`, `get_gas_used()`, `get_gas_refund()`; map addresses via `boa.env.lookup_contract`. For line-level hotspots: `boa.env.enable_gas_profiling()` + `boa.profiling.global_profile()`.
